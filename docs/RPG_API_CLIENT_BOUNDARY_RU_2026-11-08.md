# AI Story RPG — движок как API, Flutter как один из клиентов

**Решение 8 ноября 2026:** весь RPG-движок предоставляет публичный независимый API. Flutter — клиент этого API, а не владелец игровых правил. Сетевой сервис не обязателен; если понадобится, появится отдельный HTTP/gRPC адаптер, использующий те же правила.

## Уже реализованная граница

```text
   Flutter UI          Dart CLI          future native/web/HTTP adapter
       |                   |                          |
       +-------------------+--------------------------+
                           |
                    packages/rpg_api
                      API contract 0.1
                  /                      \
          RpgGameApi                 RpgAuthoringApi
               |                           |
         rpg_gameplay                 story_authoring
               |                           |
       campaign_manager              bookworld_format
               |                           |
          story_core  <---- единственный источник правил
```

**В коде этого пакета:** новый pure-Dart `packages/rpg_api` без Flutter; `LocalRpgGameApi` делегирует операции к текущему `RpgGameplayEngine`, `LocalRpgAuthoringApi` — к `BookAuthoringEngine`, `OfflineBookAnalyzer` и проверенному `PortableReviewedDraftCompiler`. Нет второго runtime, нового формата, нового файлового хранилища и новых правил.

Клиент предоставляет приватную SQLite (и управляет временем жизни), пути/планировщик isolate, интерфейс, согласия, ключи и опциональный облачный транспорт. API **никогда** не запрашивает ключи и не выполняет HTTP. Flutter `DeviceWorldLibraryGateway` и worker импорта/индекса книги используют новый API; остальные экраны будут переведены без ломки старых интерфейсов.

## Чего пока нет и что не нужно обещать

Самостоятельная компиляция из **проверенных** данных есть, но полный автоматический книжный CANON, формальная поддержка всех ролей, свободное создание новых действий AI-GM и готовый пользовательский book-to-RPG workflow пока отсутствуют. Наличие API v0.1 не устраняет эти функциональные ограничения.

## Выполненный пакет разделения authoring-логики

Реализации `NpcContinuityAudit`, `DraftSceneGraphOverview`,
`CrossActSourceEvidencePacket`, `PreparationReadinessReport` перенесены из
Flutter в `story_authoring` **без изменения алгоритмов**; локальные файлы
клиента — переэкспорты. Добавлен офлайн `BookToRpgWorkflow`, который выбирает
точную исходную редакцию/отдельную сказку, делает resumable scan и формирует
готовность с обязательной редакторской проверкой. `RpgAuthoringApi` предоставляет
эти операции другим клиентам. Чистые NPC/graph-тесты перенесены в
`story_authoring/test` в дополнение к существующим Flutter widget-тестам.
Граница импортов теперь отвергает возврат этих правил во Flutter.

## Проверяемые ИИ-предложения без Flutter

В `story_authoring` перенесены четыре проверки ответов модели и их промпты.
`rpg_api` предоставляет `RpgProposalReviewApi`, а Flutter оставляет
ключи, сетевой транспорт и явное согласие. Подробности:
[docs/RPG_AI_PROPOSAL_CONTRACT_RU_2026-11-09.md](RPG_AI_PROPOSAL_CONTRACT_RU_2026-11-09.md).

## Автономный пакет художественного оформления всей кампании

`BookToRpgWorkflow.prepareCampaignNarration` и `RpgCampaignProseApi`
выносят из Flutter формирование манифеста всех сцен из итогового
source-locked NPC/hero/item BookWorld, пакетные запросы, неизменные контексты,
проверку полного JSON-ответа ИИ, SHA256-формат контрольных точек и
проверенную финальную компиляцию. `CampaignProseFinalizer` пользуется
существующим `ReviewedCampaignProseWriter`: меняется только текст,
не события, реплики NPC, инвентарь, выборы и причинность.

Flutter теперь только клиент: показывает согласие, отправляет запросы,
сохраняет приватный файл и проверяет гонки редакций; тяжелая сборка идет
в изоляте. Модули авторства не зависят от Flutter, Z.ai, ключей и сети.
Добавлены headless tests с поддельными пакетами и source-bound BookWorld.
Это **этап после подтвержденной сборки игры**, а не автоматическое
создание литературно-канонической игры из любой книги.

## Flutter как клиент единого процесса создания RPG

Экран `WholeBookNpcCampaignPage` теперь вызывает
`RpgCampaignWorkflowApi` для подтверждения базовой игры, игровых
предметов и последствий, NPC, полного пакета художественных сцен
и итоговой проверки игрового мира. В отдельные реализации этой логики
во Flutter больше не добавляются правила `StoryWorld`.

Страница `CampaignProsePage` принимает два необязательных обратных
вызова `acceptExisting` и `applyReviewed`. В новом мастере они
ведут к `ReviewedCampaignWorkflow.completeWithoutNarration` и
`completeWithNarration`. Результат перед установкой проходит
независимую проверку причинности. Старый вызывающий код страницы
по-прежнему может использовать `CampaignProseAcceptance` — это
строгая реализация через тот же независимый компилятор, без
обхода проверки исходных цитат.

Все черновики, кнопки подтверждения, приватное хранилище, CAS,
ключи и сетевой транспорт Z.ai остались клиентскими деталями.
CI дополнительно запрещает прямые вызовы сценарных компиляторов
из главного мастера создания игры. Новые widget-тесты проверяют
обе дороги принятия текста без реальных запросов ИИ.

## Старый многоактовый редактор также подключён к единому API

`MultiActTrialPage` теперь использует `RpgMultiActTrialApi`.
Публичный Dart-адаптер `LocalRpgMultiActTrialApi` не реализует
сценарные правила повторно, а делегирует в уже принятые независимые
`MultiActTrialCompiler` и `ReviewedGameplayCompiler`. Через
этот порт проходят компиляция многоактовой игры, проверка предметов
в одном или нескольких пакетах, подтверждение выбранных эффектов и
независимая проверка итогового приватного `.bworld`.
Существующие проверки ролей, NPC, литературных согласований
и ручного выбора исходных цитат сохранены;
ключи и сеть не переносятся в ядро.

Это **одна публичная граница** (`rpg_api`) с несколькими
маршрутами сценарного авторства, а не два runtime-движка.
Отдельная задача — согласовать редакторские экраны
и режимы CANON/ALTER_FATE с общей моделью этапов, без
принудительной миграции старых `.bworld`/`.bwsave`.

## Предпросмотр сюжета и итоговая компиляция используют один компоновщик

Ранее Flutter сам выполнял `BookwideSourceEncounters.attach`,
привязку героя и NPC, а `MultiActTrialCompiler` повторял
эту логику независимо. Теперь общий чистый Dart
`MultiActTrialPlanComposer.compose` используется и основным
компилятором, и `RpgMultiActTrialApi.composePreviewPlan`.
Это предотвращает расхождение между показанным пользователю
планом, выбором предметов и реальными условиями `.bworld`.

Предпросмотр `includeNpc:false` может проверить возможность
знакомства **до** добавления NPC-флага. Прежняя ошибка, когда
уже выбранный NPC не давал показать план без своей встречи,
устранена без ослабления правил итоговой компиляции.
Дваактовые headless-тесты сравнивают составленный план с
планом исходной книги и проверяют отказ от неподтверждённого NPC.
