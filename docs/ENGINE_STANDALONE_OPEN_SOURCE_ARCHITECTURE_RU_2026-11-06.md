# Отделяемая архитектура игрового движка (текущий контракт, не опубликовано)

**Дата:** 2026-11-06. **Приоритет:** «загрузил книгу → получил готовую игру → начал играть». Движок пока остаётся набором независимых пакетов в том же GitHub-репозитории. Отдельный open-source репозиторий — будущая цель, НЕ текущий этап.

## 1. Действительные пакеты и направление зависимостей

| Пакет | Отвечает за | Не должен делать |
| --- | --- | --- |
| `packages/story_core` | Детерминированные правила, `StoryBlueprint`, `StoryWorld`, `WorldState`, проверенные события/эффекты, `CharacterId.issueNpc/isValidNpc` | Flutter, SQLite, файлы, Z.ai, `story_engine` |
| `packages/story_runtime_adapter` | Публичный `StoryRuntimeAdapter`, `StoryEngineCoordinator`, синхронизация с заменяемым `story_engine` | Править авторитетное состояние в обход `story_core`, импортировать приложение |
| `packages/bookworld_format` | Строгая офлайн-проверка `.bworld` v1/v2/v3, исходные сведения и подписанные презентационные реплики | Придумывать новую игровую логику; разрешать непроверенные ZIP/данные |
| `packages/campaign_manager` | SQLite-журнал событий, кампании, проверка сохранений и восстановление, переносимый `.bwsave` v2 | Быть единственным владельцем правил игры; требовать Flutter/ИИ |

Направление: клиент (Flutter, CLI или сторонний Dart-проект) → библиотеки. `campaign_manager` зависит от `bookworld_format`, `story_runtime_adapter` и `story_core`; `story_runtime_adapter` зависит от `story_core` и выбранного `story_engine`. Принятые изменения мира разрешает только `story_core`. Хранилище может быть конкретным адаптером; **только ядро обязано оставаться независимым от SQLite/файловой системы**.

## 2. Публичный Dart API, который уже существует

- `CharacterId.issueNpc()` — одна выдача постоянного `npc_` + 32 hex; `CharacterId.isValidNpc(id)` — единая проверка формата. ID нельзя вычислять по имени, книге, цитате или сцене. В редакторе сохраняется исходный ID.
- `StoryBlueprint.fromJson` — строгий контракт игровых сцен и правил; `StoryWorld` — независимая детерминированная модель; `StoryRuntimeAdapter` предоставляет `state`, `events`, `sceneId`, `sceneText`, `choices` (включая `enabled` и `lockReason`), `choose`, `checkpoint`.
- `StoryEngineCoordinator.start/restore` — in-memory клиент текущего сценарного адаптера. Никакого ИИ; изменения проверяются атомарно через `story_core`.
- `BookworldImporter.inspect` — независимая проверка оригинального v1, отдельные `PrivateBookworldImporter`/`RichPrivateBookworldImporter` — v2/v3; `BookworldCampaignStore.installBookworld` выполняет строгий внутренний dispatch v1/v2/v3.
- `BookworldCampaignStore.openPrivateDirectory`, `installBookworld`, `createCampaign`, `loadCampaign`, `commitChoice`, `exportPortable`, `importPortable` — рабочий без-UI маршрут SQLite/сохранений. Вызовы приложения не требуются.
- `RichSceneDialogue.parse/verify` — только презентационные текстовые реплики; не предоставляет персонажу никаких знаний или прав.

Для визуализации клиент читает `sceneText`/`choices`, для сохранения использует `campaign_manager`; интерфейс библиотек не требует Flutter. Диалоги и портреты — отдельный визуальный слой. ИИ — предлагающий слой: он не меняет мир, пока предложенная команда не разрешена `story_core`.

## 3. Доказательство независимости в CI

В `.github/workflows/android-ci.yml` добавлены обязательные проверки в job `M1.7 deterministic world and schema contracts`: `python3 tools/ci_check_engine_boundaries.py` проверяет import/export и runtime зависимости (нет переходов engine→apps/Flutter, ядро без io/sqlite), затем после генерации проверенного demo `.bworld` и тестов пакетов запускается `dart run example/standalone_rpg.dart ../../artifacts/bookworld/manor_m17_original_demo.bworld` из `packages/campaign_manager`.

CLI-проверка: строгая проверка архива → установка мира → текущая сцена/доступные и заблокированные варианты → подтверждённые решения → изменение инвентаря/знаний/флагов → экспорт `.bwsave` → фактический перезапуск SQLite → импорт переносимого сохранения → одинаковое детерминированное окончание и хэш. Нет Flutter, `apps/story_reader`, Z.ai, UI и сетевого доступа. Тесты `story_core` отдельно контролируют ID и мировые инварианты.

**Не считать эту приёмку завершённой, пока exact-head CI #127 и post-merge main не завершатся SUCCESS.**

## 4. Что по архитектуре ещё не готово

- Полная карточка NPC с биографией сейчас — частная авторская модель Flutter-приложения, а не компонент утверждённого мира. В `story_core` находится только переносимый формат/выдача постоянного ID; это намеренное разделение.
- Связи редактора и source-locked speaker→ID из PR #127 ещё не реализуют подтверждённые игровые правила изменения отношений. Не объявлять такие механики готовыми и не копировать в `story_core` текст редакторских заметок.
- `story_engine` пока фиксирован как зависимость за интерфейсом `StoryRuntimeAdapter`; интерфейс альтернативного сценарного движка ещё не тестировался.
- Хранилище SQLite уже отдельный пакет, но заменяемый storage port не вводим, пока не появится второй реальный вариант. Аналогично AI-провайдер и визуализация: клиенты/адаптеры, не части ядра.
- `.bworld` v1/v2/v3 проверяются в текущем контракте. Переносимое представление полноценной карточки NPC, отношений и источников диалогов потребует явно версионированного расширения, проверок writer/importer в Dart и независимой Python parity; без скрытой подмены v3.
- Пока не сделаны полный source-locked NPC-реестр, event-scoped knowledge/relationship effects, сквозная полноценная RPG по 2 разным русским FB2 и настоящий GLM E2E на Windows/Android. Отдельная публикация проекта/лицензирование/semver совместимость — позднее.
