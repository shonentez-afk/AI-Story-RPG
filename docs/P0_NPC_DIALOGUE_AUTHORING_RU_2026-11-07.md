## Задача

Сейчас `RichSceneDialogue.parse` берёт чередование говорящих из подписанного текста, а `RichNpcDialogueKnowledge.validate/redact` проверяет идентичность NPC, знания, доверие, память и события. Раньше автор вручную прописывал `scene_dialogue_knowledge` для **каждого** названного хода разговора. Новый `RichNpcDialogueAuthoring` составляет эту разметку **автоматически из уже рассмотренных доказательств**, без угадывания слов/семантики.

## Один автономный движок

- Новый планировщик живёт в **чистом Dart-пакете** `packages/bookworld_format`. Не импортирует Flutter, GLM, HTTP, SQLite или клиентские страницы.
- Действия, права игрока, исходы диалоговых решений остаются в `StoryBlueprint` / `story_core` / `story_runtime_adapter`. Ни один новый диалог не создаёт второе состояние игры.
- Собранная приватная игра — тот же `.bworld` rich-v3. Во время офлайн-исполнения реплики фильтруются по **committed** событиям конкретной кампании; сохранение/форк/replay остаются прежними.

## Порядок подготовки

1. Автор принимает полный художественный текст сцены в проекте и отдельно подтверждает его как частную игровую интерпретацию, а **не буквальный литературный канон**.
2. Каждое точное имя говорящего вручную связывается с `player` либо постоянным `npc_<32hex>` `character_id`. Имя само по себе не является доказательством тождества.
3. Для каждой реплики NPC выбирается **одна из двух взаимоисключающих классификаций**:
   - `reviewedNpcFactByTurn[scene_id][turn_index] = fact_id`: ранее подтверждённое событие из `npc_knowledge.grants` должно действительно дать именно этот факт этому персонажу и быть достижимым **перед** текущей сценой;
   - `reviewedSafeNpcTurns[scene_id]` включает `turn_index`: отдельное редакторское согласие на неразглашающую игровую реплику. Из названия/книги никогда не выводится знание автоматически.
4. `RichNpcDialogueAuthoring.propose` проверяет все реплики через **существующий** строгий импортный контракт `RichNpcDialogueKnowledge.validate`, формирует план и его `approvalDigest`. Это **только предпросмотр**, игровое состояние не меняется.
5. После отображения полного плана и явного подтверждения конкретного digest `RichNpcDialogueAuthoring.accept` возвращает `scene_dialogue_knowledge`. Автономный `NpcKnowledgeRichWorldBridge.prepare` принимает `reviewedDialogueProposal` и `approvedDialogueDigest` и выполняет обычный rich-v3 writer/importer.
6. При несовпадении blueprint, участников, digest, доказательства или их числа сборка отклоняется. При повторном запуске офлайн-игры только event-sourced сохранение решает, какие слова NPC разрешено показать.

## Автоматизация и что сознательно НЕ сделано

Автоматически создаётся **разметка и причинные условия** готового текста, а не фразы NPC. За их художественное соответствие характеру и книге по-прежнему отвечает отдельный просмотр автором. Событие `learn_fact` не равнозначно художественной истинности реплики, а source quote не доказывает, что именно эти слова были произнесены.

Следующий пакет разработки: единая графовая модель `source event → присутствие NPC → получение знаний → мотивы → разговор → выбор ответа → социальные/сюжетные последствия`; работа GLM **до** сборки по явному согласию и ограниченному бюджету, затем строгая редакторская приёмка в уже созданном компиляторе. Реализовать полноценные CANON и ALTER_FATE, затем две разные реальные FB2 с физическим Win/Android тестом.

## Приёмка

- Pure Dart unit/E2E: два маршрута к одной сцене, один знает факт, другой нет; replay сохраняет разграничение.
- Негативные проверки: нет NPC identity, нет подтверждения, подмена source quote, неизвестный или двусмысленный grant, неподписанный turn, digest не совпадает.
- Обычный путь приложения `compileReviewedNpcRichPrivateBookworldInWorker` принимает план, подписывает rich-v3, проверяет `.bworld` и исполняет через тот же `StoryWorld`.
- Независимый Python валидирует реальные Dart-created ZIP bytes; Flutter analyze и widget тесты, M1.7, M0, Android и Windows проходят на **точном SHA**.
