## Задание для нового чата

Продолжи разработку **внешнего Python-генератора и установленного навыка создания игр из книги**.
Начни с этого файла и текущего состояния GitHub. Не начинай проект заново и не возвращайся к выполненным этапам E1–E5.

Пользователь передаёт книгу в ChatGPT, ассистент анализирует её, пишет адаптацию и запускает внешний компилятор в своей рабочей среде. Пользователь получает готовый `.bworld v3` для импорта в приложение. Установка Python или запуск скриптов на компьютере/телефоне пользователя не требуется.

## Что уже реализовано

### Сборка и проверка

- Обычный `build` создаёт rich `.bworld v3` из принятого проекта и `enrichment.json`.
- `verify` проверяет архив и сопровождающий `.attribution.json`; `build-rich` / `verify-rich` сохранены как алиасы.
- В v3 поддержаны герой, предметы, характеристики, знания и воспроизводимые игровые последствия.
- Sidecar сверяется с содержимым проверенного архива, а не только с хешем файла.
- `doctor` проверяет закреплённые зависимости Python/Dart. Самовольное изменение контрольных сумм для обхода несовместимости недопустимо.
- Старое требование `model_provenance = none/null` относится к прежнему контракту v2. Для v3 использовать действующий компилятор и его атрибуцию; не подменять неизвестный идентификатор модели выдуманным.

### E6a — gameplay-audit

Файл: `tools/rpg_author/gameplay_quality.py`.

Проверяет достижимые сочетания сцены, флагов, инвентаря, характеристик и знаний. Находит недоступные действия, одинаковые последствия разных кнопок, декоративные ресурсы, некоторые случаи схождения веток без значимых последствий и общие концовки, требующие редакторской проверки.

Лимит — 2500 состояний. При превышении возвращается ошибка, а не успешный результат. Проверка не доказывает литературное качество.

### E6c — dialogue-audit

Файл: `tools/rpg_author/dialogue_quality.py`.

Проверяет подготовленный список тем `ai_story_dialogue_topics_v1`: вопрос, сцену ответа, подпись собеседника, доступность, ограничение по знанию и невозможность повторить одноразовый вопрос.

Проверки запускаются отдельными командами. Обычный `build` автоматически их НЕ вызывает. Python-аудит сам не пишет реплики и не исправляет сюжет.

## Исходные недостатки диалогового аудита (исправлены в E6d)

### 1. Предварительное знание проверяется после выбора

В проверке `requires_fact` используется состояние после применения эффектов вопроса (`next_state`), а не состояние до него.

Воспроизведение на синтетическом `fixture` из `tests/rpg_author/test_dialogue_quality.py`:
1. Создать пример с `requires_fact='known_truth'`.
2. Оставить начальные знания пустыми.
3. Добавить самому вопросу эффект `learn_fact: known_truth`.
4. Текущий аудит возвращает `warning_count = 0`.

Следствие: аудит не гарантирует наличие обязательного знания ДО вопроса. Закрепить явную семантику `requires_fact` как предпосылки вопроса/раскрытия ответа, проверять входное состояние и добавить регрессионные случаи: нет знания, получено заранее, получено только самим вопросом. Если нужны сведения, впервые сообщаемые ответом, они должны описываться отдельно от предпосылки.

### 2. Маршрут доказательства повторного вопроса неполный

Обнаружение повтора работает, но `example_route` составляется из путей от начала игры и может не показывать реальное повторное обращение.

Воспроизведение: `fixture(one_shot=False)`.
Аудит выдаёт `REPEATABLE_DIALOGUE_REWARD`, но маршрут равен `["ask_one"]`. Полное воспроизведение — `ask_one → back → ask_one`.

Исправить построение пути между первым вопросом и повторным вопросом. Добавить повтор с промежуточными сценами и проверить, что выданный маршрут можно последовательно проиграть по правилам и он действительно содержит два выполнения одного вопроса.

Эти случаи были воспроизведены отдельно; существующие 90 тестов их не закрывают.

## Следующие три программные задачи

1. **Исправить два недостатка dialogue-audit.**
   Добавить содержательные регрессионные проверки и обновить документацию семантики знания.

2. **Собрать единый завершающий процесс.**
   Из принятого сценария и enrichment: сборка v3 → проверка архива и атрибуции → gameplay-audit → dialogue-audit при наличии диалогов → проверка литературного отчёта → сводный отчёт.
   - Сохранить подробные причины отказа, привязку к точным входам и хешам результата.
   - Предупреждения качества должны препятствовать объявлению игры готовой.
   - Если диалогов нет, отражать это явно; отсутствие их списка при наличии диалогов не должно незаметно давать успех.
   - Структурный успех не называть доказательством литературного качества или прохождения на устройстве.
   - Название/интерфейс новой команды ещё не выбраны; это предстоящая реализация.

3. **Обновить навык на итоговую проверенную версию.**
   Закрепить точный коммит после исправлений и проверок. Включить единый процесс в обязательный порядок работы и выдачу результата.
   Создание диалоговых тем, проверку причинности и осмысленных последствий включить в авторский проход по книге.
   Не разрабатывать миграцию E5: пользователь её исключил.

Порядок реализации можно объединить в один небольшой этап: исправления → единый процесс → проверки → обновление закреплённой версии навыка.

После программных задач: создать/проверить игру новой версией и пройти её в актуальном приложении на телефоне — диалоги, предметы, журнал, сохранение, закрытие и повторное открытие. Для заявления о поддержке Windows нужен отдельный реальный Windows-проход. Если устройства недоступны, не выдавать CI за такую проверку.
