# AI Story RPG — создание из книг настоящих 2D-пиксельных RPG с ходьбой по миру

**Дата:** 7 ноября 2026. **Статус:** архитектурное решение и план, не работающий код. Нормативное дополнение к [генеральному плану](AI_STORY_RPG_COMPLETE_GAME_UNIFIED_SPEC_RU.md), [процедурным пиксельным сценам и скинам](PER_BOOK_DYNAMIC_SKIN_DESIGN_RU_2026-11-07.md) и [готовым Web-выпускам для Яндекс Игр](WEB_STANDALONE_YANDEX_GAMES_PLAN_RU_2026-11-07.md). Главная цель P0 полной текстовой игры по реальной книге остаётся первоочередной.

## 1. Принятое направление: единый сценарный движок + Flame для 2D прогулок

**Рекомендуемый стек:**
- **AI Story RPG / story_core (уже существует):** источник истины для сцен, событий, знаний, отношений, предметов, доступности действий, последствий, концовок, журнала, сохранений, source evidence и NPC identity.
- **Flame (будущая новая зависимость Flutter, а не отдельная игра):** игровая 2D-сцена top-down с камерой, управлением персонажем, физическими препятствиями, локальными действиями, анимациями движения, interactable zones и процедурными декорациями.
- **Наш программный PixelRecipeRenderer:** общие palette, style_seed, procedural geometry, tiles, characters, particles и icons — **не** AI PNG, не обязательные raster sprites. Flame использует их для элементов мира, Flutter — для рамок диалогов/панелей.
- **Flutter UI:** диалоги и текст читаемым русским шрифтом, варианты сюжетных решений при необходимости, три панели «Герой / Предметы / Журнал», меню, настройки, touch controls, сохранения. Flame GameWidget/Overlays помещает Flutter UI поверх игрового мира. Не дублировать выборы и журнал в Flame-состоянии.
- **Python/навык:** готовит источник → литературно проверенный сценарий → spatial content definitions (локации, карты, размещение NPC, предметы, переходы, triggers) и cosmetic recipes; **не** пишет GDScript, Flutter/Dart код под каждую книгу и не создаёт отдельный exe.

**Flame** подходит, потому что уже работает в Flutter/Web и поддерживает World/CameraComponent, collisions, inputs/JoystickComponent, GameWidget, overlays. Официальные источники: [Flame](https://github.com/flame-engine/flame), [GameWidget](https://docs.flame-engine.org/latest/flame/game_widget.html), [Camera & World](https://docs.flame-engine.org/latest/flame/camera.html), [Collision Detection](https://docs.flame-engine.org/latest/flame/collision_detection.html), [Joystick](https://docs.flame-engine.org/latest/flame/inputs/other_inputs.html), [Flutter Overlays](https://docs.flame-engine.org/latest/flame/overlays.html), [flame_tiled/Tiled](https://docs.flame-engine.org/latest/bridge_packages/flame_tiled/flame_tiled.html). Стандартная collision detection определяет **факт пересечения**, а корректную реакцию (не проходить через стену / trigger / pick up) реализует игровой слой.

**Граница против другого engine:** Godot лучше рассматривать только для отдельного более тяжёлого экшена, платформера/физики, а не как обязательный второй runtime. Иначе придётся переносить или связывать Dart story_core с GDScript/Godot, отдельно проверять многоплатформенные сейвы, NPC-правила, безопасность, два набора UI и HTML5/WebAssembly. [Godot Web Export](https://docs.godotengine.org/en/4.5/tutorials/export/exporting_for_web.html) требует WebAssembly/WebGL2 и имеет web/mobile оговорки. **Flame не заменяет story_core; это графический и пространственный слой.**

## 2. Три способа игры из одной книги

| Режим | Внешний вид и управление | Когда выбирать |
| --- | --- | --- |
| **NARRATIVE** (существующая цель P0) | Текст, подписанные реплики NPC, доступные сюжетные выборы, иллюстрации | Любые книги, особенно камерные разговорные истории, без подтверждённой карты |
| **EXPLORE_2D** (новая цель после P0) | Игрок ходит по локациям, исследует, подходит к NPC/объектам, нажимает «Взаимодействовать», подбирает реальные предметы, открывает двери/задания; диалоговое окно появляется в нужный момент | Книги с конкретными местами, исследованием, предметами и пространственными событиями |
| **HYBRID** (предпочтительный будущий автоматический режим) | Прогулочные сцены чередуются с длинными литературными эпизодами; разговоры/решения оформлены Flutter overlay, остальное — перемещение и взаимодействие | Большинство полноценных сюжетных RPG, когда структура книги допускает исследование |

**Никаких обязательных однотипных меню «Выбери вариант A/B» на каждом шаге прогулки**: ходьба не требует story_core choice. Но когда герой говорит/передаёт предмет/берёт ключ/изменяет отношение/заканчивает цель — клиент передаёт существующий или новый согласованный typed `ActionIntent` в story_core; проверенные условия и последствия остаются авторитетными. Если два исхода литературно различаются, нужно дать доступные физические или диалоговые способы выбрать их, а не маскировать выбор под автоматическую случайность.

**Не каждую книгу принудительно делать RPG с ходьбой.** Автоматический content analysis оценивает достоверность/полезность локаций, NPC и пространственных действий. При отсутствии данных выбирать NARRATIVE или HYBRID с минимальными локациями; не заставлять игрока 10 минут ходить ради одного абзаца.

## 3. Какие данные должен создать генератор

Сначала полная проверенная BookEvidenceGraph/StoryPlan/NPC, затем:

1. **LocationGraph:** реальные/адаптированные места, доступность по главам/условиям, вероятные переходы, устойчивые location_id и связь с source assertions. `SOURCE_PASSAGE` против `EXPLICIT_ADAPTATION` — обязательная пометка. Не утверждать, что вымышленная планировка замка содержалась в тексте книги.
2. **MapLayoutRecipe:** компактная top-down карта по клеткам (например, 16/32 px логических тайла), размеры/границы, seed, уровни пола/стен, проходы, двери, зоны воды, препятствия, безопасные точки spawn, collision masks, вход/выход. Грамматики комнат, деревень, лесов, дворцов; без ручного копирования Tiled/PNG под каждую книгу.
3. **ProceduralTileStyle:** материалы/цвета/орнаменты и пиксельные формы из единого StyleBible, как в рамке текста и иконках. Не хранить заранее нарисованные pixel tilesheets; вычисляемый runtime cache допустим.
4. **ActorPlacement:** player spawn, постоянные NPC character_id и видимость/жизненный статус из принятого npc_social v1–v5; позиции NPC, facing, маршрут/idle анимации, доступность диалога. Персонаж, ушедший из истории, не должен стоять на карте только потому, что так нарисовал скин.
5. **InteractablePlacement:** item_id, объект, расстояние взаимодействия, предметный/диалоговый `action_id/choice_id`, preconditions, эффекты и ссылки на source. Подход к предмету **не равен** взятию в инвентарь, пока core не подтвердил действие.
6. **Quest and Scene TriggerGraph:** вход в область, завершение перехода, взаимодействие с NPC, близость к объекту → предложение действия; настоящие `WorldEvent` только после validated commit. Скрытые сюжетные главы/секреты нельзя породить картой раньше времени.
7. **WorldTransition/SaveAnchor:** место возрождения, кампания, версия пакета, position/heading, map/content hash, checkpoint и состояние дверей из события; допустимый восстановимый маршрут для каждого исхода.

**Новый отдельный schema contract:** `exploration_2d_v1` / `map_recipe_v1` (имена проектные). Не помещать такие поля в нынешний private rich .bworld v3: его Python writer/Dart importer контролируют строго четыре ZIP entries, а новых map capabilities пока не существует. Нужна согласованная новая версия/capability вместе с Python writer/verifier + Dart importer + story_core action adapters + SQLite/save migration.

## 4. Движение ≠ сюжетные события: где хранится состояние

**Непрерывное локальное состояние Flame:** position, velocity, facing, interpolation, camera, animation frame, movement path, pointer/joystick. Не писать WorldEvent 60 раз в секунду, иначе журнал/SQLite/хеши развалятся.

**Долговременное игровое состояние:** committed actions (NPC dialogue/learn_fact, acquire/transfer/consume item, quest objective, open door, end scene) только в story_core и кампании. Смена локации и checkpoint spawn должны сохраняться через отдельно версионированную projection/compact save; определять, какие пространственные состояния влияют на сюжет, а какие остаются локальным snapshot. Save при открытии/закрытии, переходе карты и подтверждённых действиях. Перезапуск на Android и Web должен восстановить героя в достижимой точке без дублирования loot/событий.

**Инварианты:** повторный tap не может взять предмет дважды; проход через стену невозможен, заблокированные двери закрыты, key gating не обходится координатами; NPC, отсутствующий/умерший по story_core, не отображается доступным; фон/пиксели не меняют судьбу мира; все события совпадают с replay и журналом.

## 5. Контроль движения

- **Windows:** WASD/стрелки — движение; E/Enter/Space — действие; Escape — диалог/меню; Tab/I/J — герои/предметы/журнал только при проверке конфликта хоткеев.
- **Android:** небольшой виртуальный joystick **или** tap-to-move с простым pathfinding, крупная контекстная кнопка «Взаимодействовать»; скрывать ненужные элементы при чтении, безопасные отступы.
- **Web/Яндекс Игры:** та же top-down карта, keyboard/touch, fixed embedded game, Yandex SDK/контекстные паузы и компактный save; **не** GLM/free-text interactive AI на портале. Без произвольного импорта чужих игр в standalone.
- **Доступность:** альтернативное управление и опция «Пропустить перемещение / Перейти к доступной точке сюжета» для игроков, которым сложно ходить; маршрут не должен превратиться в несправедливый замок без варианта пройти литературную часть.

## 6. Генерация карт, карты должны быть проходимыми

Основная трудность **не** нарисовать плитки, а создать *осмысленный проходимый игровой мир по книге*. Не путать `scene graph` (причины истории) и `spatial graph` (куда герой может идти). Оба должны быть связаны:

- Topology first: комнаты/переходы/ландшафт/ключевые задачи/доступ NPC → граф проходов → расстановка стен/декора → живой pixel renderer.
- Seeded layout: одна книга, ревизия, map_id и seed дают одинаковый план. Варианты при пересборке только явно.
- A*/BFS flood-fill проверяет **каждую** значимую точку spawn, выход, предмет, NPC interaction, сейв, альтернативную концовку. Для ключа и закрытой двери проверять достижимость *до и после* разрешённого события; нельзя заблокировать предмет за дверью, открываемой тем же предметом.
- Локации, которые в книге не описаны, отмечать `EXPLICIT_ADAPTATION` в evidence; генератор вправе добавить связующий коридор/площадь для gameplay, но нельзя молча менять смысл произведения.
- Усложняющие алгоритмы WFC, шум, BSP-room splitting, path variants и декор применять **после** проверки ключевой топологии. Они не должны превращать карту в лабиринт, где нельзя пройти сюжет.
- Живые NPC могут двигаться по локальным маршрутам, но важные gameplay transitions должны проходить через нашу engine action approval, а не через свободное локальное перемещение.

## 7. Пример прогулочного эпизода «Король-лягушонок» (только модель, не готовая адаптация)

Игрок управляет принцессой на дорожке рядом с прудом. Может пройти к деревьям, осмотреть воду и поговорить с лягушонком. Если сюжетный факт подтверждён литературным анализом, найденный/уроненный золотой мяч отмечен `item_id`, взаимодействие с ним — отдельный проверенный action. Подошёл к лягушонку → Flutter overlay диалога с настоящим NPC `character_id` → герой может пообещать награду или отказаться, и **только** validated story_core choice меняет отношение NPC и дальнейшую ветку. Позже переход во дворец открывает другую map/спавн. NPC знает ровно то, что мог узнать по source/events. Каждый ход игрока по дорожке **не** записывается в журнал как поступок.

## 8. Flame или Godot?

| Критерий | Flame + Flutter (рекомендация) | Godot отдельным клиентом |
| --- | --- | --- |
| Совместимость с Dart story_core и текущими Flutter widgets | **Одна среда Dart**; GameWidget/Overlay, общий gateway/сейвы и русские Text | GDScript/Godot требуют междвижкового протокола/порта моделей; риск вторых правил/сейвов |
| Пиксельная графика без AI-картинок | Общий CustomPainter/Canvas и data-only pixel recipes, Flame рисует world/camera | Хорошие TileMapLayer/AnimatedSprite2D и процедурные drawing APIs, но второй renderer |
| Top-down walking, camera, NPC collisions, pick up | Есть компоненты World/Camera/collision/input, логика квестов остаётся ours | Есть зрелые scene/nav/collision инструменты; избыточно для первых прогулочных RPG |
| Web/Яндекс Игры | Flutter Web и Yandex JS SDK adapter, один build target | WebAssembly + WebGL2, export/browser limitations и отдельный SDK adapter |
| Сложный real-time platformer / боевик / сильная физика | Дополнительный специализированный код/библиотеки | Рассмотреть позже как **отдельный экспортный renderer**, но общую story state сохранять |

Другой движок имеет смысл **только если** после прототипа убедимся, что для наших книг важны real-time combat, сложная физика или полноценные platformer levels, которые Flame будет значительно дороже поддерживать. Переносить главную игру в Godot сейчас не нужно.

## 9. Работы и приёмка, чтобы не затягивать P0

**P0:** нынешняя главная задача — полностью рабочая литературная текстовая RPG по реальной книге на Windows/Android; никаких новых maps в действующий v3, никаких новых обязательных редакторов.

**P1 prototype (после P0):** взять один синтетический исходник, сделать одну небольшую seeded top-down карту: герой, NPC с stable ID, один предмет, блокировка прохода, диалог и инвентарь из существующего story_core. Flame/Flutter widget в отдельном безопасном sandbox-примере. Без map capability в действующий v3. Контролировать 60 FPS на типичном мобильном устройстве как **целевую метрику** (не уже доказанную).

**P2 функциональный пакет (объединить с pixel scene/skins, когда доказана архитектура):** BookLocationGraph, procedural layout, проверка reachability, map/actor/interaction recipes, Flame runtime, Flutter overlays, versioned source-locked BookWorld schema + Python writer/verifier/Dart importer + Web standalone bridge, save/replay, Android/Windows device QA. Делать один функциональный PR с согласованной приёмкой, а не PR на карту, движение, рамки и NPC по отдельности. Не пытаться генератором писать Dart под каждую книгу.

**Дальше (опционально):** AI-driven бродячие NPC, усложнённые физические системы, бой, platformer mechanics, Godot exporter — только если нужны жанрам, имеют отдельные versioned contracts и проходят real devices/authorization.

**Критерии:** 2 разных пути, минимум 2 концовки, карта достижима, 2–3 разговора с разными NPC, получение/передача предмета через engine, нет спойлеров из будущей главы, восстановление сейва точно в достижимой точке, Android touch, Windows keyboard, Web standalone при его готовности, старая narrative v3 работает. Синтетическая demo ≠ полноценно созданная игра из реальной книги.

**Граница полномочий внешней ветки:** меняются только документы/инструменты tools/rpg_author и tests/rpg_author; main/apps/packages не затрагивать без отдельного поручения. Публикация приватной книги/текста/артефактов запрещена.
