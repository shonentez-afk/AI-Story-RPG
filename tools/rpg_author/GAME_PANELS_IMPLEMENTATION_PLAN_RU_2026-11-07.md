Внешний E6f 0.3.0a4 технически совместим на [Actions #42341605734](https://github.com/shonentez-afk/AI-Story-RPG/actions/runs/42341605734), см. Заявление «у нас нет владельцев предметов вообще» относится к прежнему срезу и теперь устарело. Это обновление плана, UI-код здесь не изменён.

**Обзор и первичные ссылки:** [GAME_PANELS_REFERENCE_AUDIT_RU_2026-11-07.md](GAME_PANELS_REFERENCE_AUDIT_RU_2026-11-07.md). **Поток:** FB2/TXT → доказательства/сюжет → versioned .bworld → BookworldImporter → StoryRuntimeAdapter + campaign_manager(SQLite) → WorldLibraryGateway.load() → immutable WorldGameView → read-only панели. **Мутация:** пользователь выбирает доступный action/choice → gateway.choose() → story_core atomic commit и event → replay/SQLite → новый WorldGameView → обновление панелей.

**Правило целостности:** UI-проекции можно пересоздавать сколько угодно. Ни текст, ни картинка, ни AI summary, ни сообщение «получен предмет» не имеют права создавать отдельное состояние, которого нет в committed WorldEvent/WorldState. Проверки доступа выполняются до рендера скрытого содержимого.

## 1. Единый UX на телефоне и Windows

### 1.1 Постоянные точки входа

Нижняя компактная панель **Герой | Предметы | Журнал** остаётся единственной игровой навигацией. Не вводить постоянные кнопки «Квесты», «Знания», «NPC», «Диалоги», «Карта», «Навыки». Всё это вложенные разделы в соответствующей существующей панели **и только когда книга действительно предоставляет такие данные**.

- **Android:** Material bottom sheet с SafeArea и корректной работой системной клавиатуры; прокручиваемое содержимое до ~80–85 % высоты; крупные зоны касания не менее 48 logical pixels; закрытие без потери позиции игры; долгие названия и увеличенный шрифт не обрезаются. Нижняя панель подчиняется текущему ReaderChrome (в полноэкранном чтении появляется при касании, не нависает над художественным текстом).
- **Windows:** тот же data/view model, но боковая панель/адаптивное диалоговое окно, keyboard focus, Tab/Shift+Tab/Enter/Escape, скролл мыши; сюжет не сбрасывает позицию при открытии/закрытии.
- **Общий стиль:** иконка + короткий заголовок + 1–2 строки описания + при необходимости разворачиваемая подробная карточка. Семантические метки для screen reader, contrast/dark theme, reduced motion, единые пользовательские настройки шрифта/межстрочного интервала из ReaderSettings.
- **Пустые состояния:** «Пока ничего не найдено» для реального пустого инвентаря; отсутствующие типы механик не отображать вообще. Для произведения без навыков или квестов не рисовать бессмысленные табы/показатели 0.
- **События при изменении:** ненавязчивое уведомление только после успешного committed action: «Получен ключ», «Открыто сведение», «Цель выполнена». Уведомление — проекция факта, не механизм изменения.
- **Никакой обязательной настройки игроком:** все отображаемые русские названия и описания приходят из проверенного пакета; локальные портреты опциональны, отсутствие картинки не блокирует диалоги.

### 1.2 Базовые компоненты Flutter (предлагаемые, ещё не созданные)

Оставить GamePanel/GameQuickBar и WorldPlayPage; вместо плоского генератора строк _WorldInfoSheet использовать единый **GamePanelSheet** с адаптивными слотами: **HeroPanelView**, **InventoryPanelView**, **JournalPanelView**. Ввести read-only **WorldPanelProjectionBuilder** (может быть частью существующего gateway, без новой библиотеки), возвращающий чистые immutable DTO, и небольшие компоненты ItemCard, JournalEventCard, StatRow, KnowledgeChip. Ни один из них не импортирует изменяемый StoryWorld.

Ключи элементам назначать по стабильным item_id / event sequence+hash / npc character_id; не по видимому имени. При перестроении UI после выбора сохранять только безопасный scroll/filter state. Данные из другого campaignId/revision не использовать.

## 2. Вкладка «Герой» — не просто список цифр

**P0 (имеющиеся данные):**
1. Шапка: имя/описание, глава/текущая сцена, необязательный доступный портрет. Если герой не указан в пакете — нейтральный заголовок, без выдуманной биографии.
2. **Характеристики:** именованные stat rows с текущими значениями. Предлагать подпись изменившего их решения, если источник есть в journal. Не устанавливать произвольные уровни, здоровье или силу.
3. **Открытые сведения:** факты только actor=player, причём из подтверждённого состояния. Нельзя показывать справочник по всей книге, включая секреты будущих глав.
4. **Краткий прогресс:** текущая сцена, игровая ревизия/время как пользовательский смысловой индикатор; внутренний tick/revision/sha не показывать крупными техническими надписями. Если нет достоверных игровых часов, не маскировать tick под часы.

**После принятого social-контракта:** раздел «Отношения» только для встреченных/разрешённых NPC; имя и роль из однозначно подтверждённого character_id; отношения направленные (герой → NPC, NPC → герой), не выводить «дружит» автоматически из случайного совпадения чисел. Обязательна source-/event-bound проверка допустимости: отображение отношений не раскрывает secret, недоступный герою. Не включать социальный раздел до подтверждённой передачи social projection через gateway.

**P1, исключительно по книге:** «Умения» с SkillDefinition и deterministic SkillCheck; уровни, XP, вероятности и cooldowns только если выбранный жанровой профиль действительно их определяет. Для литературного путешествия достаточно смелости/наблюдательности как stat gate без системы уровней.

## 3. Вкладка «Предметы» — коллекция вещей с настоящими действиями

### 3.1 P0: карточка существующего inventory Set<String>

Герой видит только актуальные item_id, преобразованные importer-verified item_names/item_descriptions. Карточка: название, описание, опциональная иконка/рисунок только по доступному локальному ресурсу/проверенной визуальной рецептуре. Кнопка «История» показывает event получения/расхода, если такие факты действительно можно восстановить. Поиск/алфавитная сортировка допустимы только в UI, не влияют на игру.

**Сейчас количество не показывать**, кроме подразумеваемого одного уникального item; не писать «x1» как модель десятков экземпляров. «Использовать/Передать/Экипировать» в P0 не добавлять автоматически: пользователь может выполнить ровно те выбора/действия, которые текущий StoryRuntimeAdapter уже разрешает в сцене. Если конкретный choice связан с предметом, карточка может предложить **переход к соответствующему разрешённому выбору**, а не самостоятельно применить эффект.

> **Примечание E6f:** v3 уже делает NPC custody/transfer для проверенных уникальных предметов. В данном разделе будущие OwnedItem/ItemActionDefinition — варианты расширения для несуществующих quantity/stackable/equip и общих ownership-моделей, **не** предложение переписать принятый ledger.

### 3.2 P1: расширенная модель предметов (новая версия контракта)

Три слоя:
- **ItemDefinition** — item_id, display_name, description, category enum (quest/consumable/equipment/document/other), stack_policy unique/stackable, optional max_stack, optional visual_ref, source_assertion_ids/provenance. Все поля только если есть основание в книге; category не угадывать по названию.
- **OwnedItem / InventoryState** — item_id, owner_actor_id, quantity, state available/consumed/transferred, acquisition_event_id; для уникальных предметов один актуальный owner во всём мире, иначе error; отсутствие/уничтожение — отдельное состояние, не произвольное скрытие UI.
- **ItemActionDefinition** — action_id/choice_id, required_item_id, allowed_actor_id и verified target_actor_id при передаче, preconditions, effects, source_link; список доступных действий вычисляет только story_core. Кнопки видны с корректным enabled/disabled reason, нажатие идёт через gateway.choose() с expectedRevision/idempotent actionId.

В новом core потребуются typed effects (названия рабочие, **не утверждённый v3 API**): acquire_item, consume_item, transfer_item, equip_item/unequip_item — последнее только для игровых книг, где существует equip slot. Инварианты: нельзя получить отрицательное количество, списать отсутствующий предмет, передать одному и тому же уникальному предмету двух владельцев или совершить действие после отката/удаления сохранения. Реальное владение NPC — не текстовое утверждение модели.

### 3.3 Пример сценария для проверки

«Герой нашёл ключ» → подтверждённый effect acquire/grant → предмет отображается → журнал ссылается на scene/choice/event получения → «Передать ключ лягушонку» доступно только при наличии ключа, присутствии допустимого NPC и требуемой сцене → committed transfer → предмет исчезает из кармана, новое владение и отношение подтверждаются event → после закрытия/перезапуска точное состояние восстанавливается. Если у текущего v3 нет transfer effect, в P0 не имитировать его через надпись.

## 4. Вкладка «Журнал»: единая дверь к ЧЕТЫРЁМ разным данным

**Не смешивать семантику:** сохранённая игровая история, текущие задачи, открытые сведения, показанные реплики — разные проекции, а память онлайн-ИИ ещё и пятый отдельный контекстный слой.

### 4.1 События (P0, уже есть источник)

Показывать временную шкалу **commit-verified WorldEvent** в последовательности истории: sceneTitle, choiceLabel, фактические дельты item/stat/player knowledge из существующего replay в WorldLibraryGateway. Структурировать как EventCard с номером/названием, типом изменения, возможностью раскрытия деталей и фильтром «Все / Изменения»; если данных мало — один список, без пустых вкладок.

Переход «Событие → Предмет/Сведение/Герой» осуществляет **navigation intent** в UI; он не запускает повторное действие. Для полноценного перехода P1 расширить read-only WorldEventView безопасными event_id/choice_id/event_hash и typed deltas, полученными из committed log. Человекочитаемая подпись и карта не являются primary key.

### 4.2 Задания / обещания (P1; существующий event log ≠ QuestSystem)

Журнал задач не должен быть «списком последних решений под другим заголовком». Ввести **QuestDefinition**: quest_id, title, description, optional giver_actor_id, optional place_id, source/EXPLICIT_ADAPTATION, ordered objectives, dependencies, visibility/secret conditions, start/success/failure/abandon transitions, optional outcomes/rewards; связывать с event/cause и quest state. Ввести **QuestState** по кампании: hidden | available | active | completed | failed; для каждой ObjectiveState: hidden | active | completed | failed. Состояние меняется детерминированным typed effect внутри того же атомарного выбора (start_quest, unlock_objective, complete_objective, complete_quest, fail_quest) или из проверяемого вычисления над committed facts/events (решение выбрать одно и зафиксировать в спецификации; не два конкурирующих механизма).

Отображение: «Активные / Завершённые / Проваленные», цель, ближайший шаг, кто попросил, событие, почему задача изменилась; не показывать скрытые альтернативы и спойлеры. Для сказки «сдержать обещание» может быть один narrative obligation, а не XP-награда и пять пустых шаблонных квестов. Неразрешимое обещание должно иметь осмысленное последствие, не вечное активное состояние.

### 4.3 Сведения / персонажи / места (P1 при наличии source-bound каталога)

Player-facing энциклопедия строится из **KnownFact** (actor=player), известных мест и подтверждённых контактов/character_id. Карточка NPC: открытое имя, роль, **только известные игроку** сведения, уже пережитые события с этим NPC, возможные отношения в допустимой трактовке. Псевдоним не становится character_id без литературного подтверждения; имя-двойник не объединять. Новые страницы/секреты не выводятся из сырого FB2, LLM summary, авторского редакторского NPC dossier или чужого social memory.

При отсутствии достаточного источника карточка остаётся краткой или не показывается; не генерировать ложный канон. Для факта есть точная связь с learn_fact event/citation или начальным одобренным знанием; сведения, которые знал только NPC, не становятся доступными герою.

### 4.4 Диалоги (существующий локальный history + будущий межсценовый)

**Уже есть:** SceneDialogueStage показывает последовательность и локальную историю **текущей** сцены, DialoguePositionStore сохраняет cursor для campaign/scene/revision. Не объявлять весь журнал разговоров готовым.

**P0:** оставить рабочий current-scene history на месте, добавить в основном Журнале понятную ссылку «История текущего разговора», только если текущий разговор действительно есть и реплики уже разрешены. Скрытый текст ни на мгновение не попадает в UI.

**P1:** versioned **DialogueDisplayRecord** (не WorldEvent): campaign_id, world_hash, scene_id, revision, turn_id или индекс, resolved speaker_character_id, verified text snapshot/hash, visibility gate result, actually_displayed_at_order, source dialogue revision. Писать в локальное приватное хранилище только **после проверки знающего говорящего** и фактического предъявления реплики. «Пропустить разговор» не является доказательством, что игрок увидел все строки; skip не добавляет не показанные строки в просмотренное. На restore/переключении ветви/reinstall показывать только элементы текущей кампании и допуска источника; историю другой ветви/старого world_hash и закрытые знания не подмешивать. При отсутствии надёжного per-turn identity не обещать полную историю, оставить существующий stage history.

**Уровни доступа:** авторские source цитаты, подтверждённое знание NPC, фактически показанные реплики, committed выборы, неавторитетные AI разговоры — разные типы данных. Память AI Town/AI Dungeon допускается только как opted-in контекст, не создаёт learn_fact или изменения отношения.

## 5. Предлагаемый контракт данных: v3 projection отдельно от будущего vNext

### 5.1 Безопасный P0, НЕ требующий менять четыре ZIP entries v3

На стороне UI/адаптера создаётся transient **GamePanelViewModel** (название рабочее): campaignId, worldHash, revision, stateHash, heroCard из существующих имён/stats/knownFacts, inventoryCards из Set + item_names/descriptions, journalEventCards из replay WorldEventView. Эти DTO **не сериализуются как новая игровая механика**, не перезаписывают .bworld, не создают предметы и не влияют на checkpoint. Любое содержимое строго привязано к фактическим snapshot/revision и обновляется после choose.

Никаких скрытых JSON «квестов», item_owner, XP или portrait URLs поверх строгого v3 без оформленной version/capability. Нативный v3 имеет ровно четыре проверенных ZIP entries; optional NPC grants PR #131 и будущий social PR #132 требуют собственной проверки принятого контракта и exact-head parity.

### 5.2 Предлагаемые схемы vNext, это НЕ поддерживаемый сегодня формат

~~~json
{
  "format": "gameplay_panels_vnext_draft",
  "capabilities": ["items_ownership_v1", "quest_objectives_v1"],
  "items": {
    "golden_key": {
      "name": "Золотой ключ",
      "category": "quest",
      "stack_policy": "unique",
      "source_assertion_ids": ["a_key_found"]
    }
  },
  "quests": {
    "keep_promise": {
      "title": "Сдержать обещание",
      "visibility": "revealed_by_committed_state",
      "objectives": ["find_friend", "fulfil_promise"],
      "source_assertion_ids": ["a_promise"]
    }
  }
}
~~~

Этот JSON — **иллюстрация логического контракта**, не готовая схема ZIP/ABI. Перед реализацией отдельно согласовать exact schema, version/capabilities, модель effects и Dart/Python/SQLite parity. Не помещать его как произвольное поле в v3. Для Quest state и owned-item state потребуется спроектировать обновлённые immutable WorldState/WorldEvent и copy-on-write replay, а не редактировать SQLite вручную. Для отсутствующих в книге механизмов capability отсутствует и UI соответствующий раздел скрывает.

**Разделять data tiers:**
- **BookEvidenceGraph:** кто, что, когда, откуда; точная цитата, степень уверенности и права на использование; не игровые изменения.
- **GameScenarioGraph:** одобренные сцены/выборы/факты/владение/quests/skills/условия/эффекты.
- **Runtime:** авторитетный committed state/events, только разрешённые изменения.
- **Presentation:** безопасные имена, описания, портреты и фильтры, которые не создают исход событий.
- **Local UX:** scroll state, показанные строки диалога и предпочтения, не авторитетные факты.
- **External AI memory:** untrusted optional context с явным consent и ограниченным retention, без прямых game effects.

## 6. Что должен автоматически делать внешний авторский навык до импорта

**Этап A — анализ полной книги.** Извлечь source-bound героя, все значимые вещи, факты, ключевые события, передачи, поручения/обещания, потенциальные характеристики/проверки, привязки NPC по character_id, возможные читателю известные сведения. Для каждого литературного утверждения указать источник и степень уверенности; inferred ≠ canon. Не добавлять sword/HP/XP/quest, если они не служат книге.

**Этап B — игровой сценарий.** Каждая приобретённая/потерянная вещь и изменение знания причинно связаны с проверяемым choice/effect, каждая задача имеет условия начала/достижения/провала, все NPC знают только допустимое, вся смена отношений имеет причинный committed event. В CANON сохраняется исходный смысл и отмечается адаптация; в ALTER_FATE разные пути дают разные последствия, а не косметические сообщения.

**Этап C — presentation.** Заполнить только реальные русские имена предметов, краткие описания, подписи, допустимые категории/иконки, тексты целей и безопасные карточки из уже одобренного графа. При отсутствии данных оставить пустой каталог или условный раздел невидимым. Никаких обязательных пользовательских ручных правок.

**Этап D — QA перед выдачей.** Exact source identity, предметная причинность, одно владение уникальным item, нет потребления отсутствующего, связанные quests завершены или обоснованно провалены на каждом достижимом исходе, NPC access gate, журнал не расходится с replay, отсутствует раскрытие скрытого текста, две содержательные концовки. Сначала закончить текущий E6e finalize/verified v3 и полноценное прохождение настоящей книги; для новых capabilities отдельно расширить E6 finalization и синтетические/реальные tests, **не объявлять их сегодня готовыми**.

## 7. Транзакционный сценарий взаимодействия и защита от ошибок

1. Открытие Героя/Предметов/Журнала вызывает чтение того же immutable WorldGameView с фиксированным campaignId/worldHash/revision; при устаревшем snapshot UI явно перезагружает, не показывает кэш соседнего сохранения.
2. UI выводит только видимые по текущему состоянию поля; секрет NPC и ещё не услышанная реплика отсекаются в importer/gateway **до** карты/поиска/истории/портрета.
3. При клике контекстного действия source-linked item/quest/UI находит разрешённый **существующий** choice_id, использует actionId + expectedRevision через gateway.choose(), ожидает committed result; неопознанный свободный запрос не создаёт effect.
4. После успешной транзакции UI строит заново герой/inventory/journal; event обеспечивает одни и те же последствия при reload, export/import save и независимом replay.
5. Повторный tap, stale revision, падение процесса, потеря сети/API timeout и две параллельные кампании не дублируют item/quest/XP и не раскрывают секреты.
6. Переключение кампаний/смена книги очищает все чувствительные локальные представления другой истории; локальные изображения и личная память не копируются между кампаниями автоматически.

## 8. Пакеты реализации: НЕ заводить PR на каждую кнопку/поле

### Пакет UI-P0 — «Три действующие вкладки, единая приёмка»

**Входит:** read-only projection и карточки существующих hero/stats/knownFacts, items names/descriptions, событий из replay; адаптивный Material sheet/Windows panel; фильтр событий, empty state, ссылки без state mutation; dark theme, шрифт, доступность, reader chrome. Не входит: новые quests, quantities, ownership, skill XP, full dialogue persistence, обязательный портрет.

**Точки изменений основного проекта (предложения):** apps/story_reader/lib/game_panels.dart; world_play_page.dart; world_library_gateway.dart (только при необходимости безопасных immutable DTO), новые маленькие UI widgets в apps/story_reader/lib/; widget tests + Android/Windows visual QA. **Без изменений story_core и .bworld v3.** Один функциональный PR с одним acceptance set после проверки реальной книги, не отдельные микропиары.

**Готовность:** «Король-лягушонок» и ещё одна независимо обработанная книга показывают корректные три раздела; 2 пути, минимальная/пустая инвентарная модель, recovery после kill/reopen, FontScale 200 %, keyboard/mobile, нет пропажи выбора при modal.

### Пакет NPC-P0 — «Только подтверждённые знания/отношения в интерфейсе»

**Объединять с уже идущим основным NPC/social пакетом (#132 или принятым преемником), не заводить отдельный PR на отображение trust.** После точной версификации scene presence/observed events/actor-scoped memory/relations проверить gateway projection: доступные NPC, безопасные знакомства и направления отношений. Без импорта неразрешённых редакторских NPC dossiers в игру. Никакого преждевременного «NPC summary» через LLM.

**Готовность:** NPC до встречи не появляется в справочнике, секрет не появляется до learn_fact, переименование не меняет character_id, изменения отношений связаны с committed choice, после save/replay значения идентичны. Если social пакет ещё draft — этот UI шаг ждёт принятого API и не блокирует UI-P0.

### Пакет GAME-P1 — «Инвентарь+задачи+условия+журнал, одна система последствий»

**Входит одним связанным PR:** согласованная item ownership/quantity/category и quest/objective contract, при необходимости skill checks, source-bound авторская подготовка, Dart core typed effects and deterministic replay, Python writer/verifier, Dart importer, SQLite/portable save, Flutter panels и функциональный E2E. Не делить по полю/вкладке: пользователь должен закончить цепочку «найти предмет → решить задачу → передать предмет → изменить отношения → увидеть и восстановить последствия». Если сценарий не требует item quantities и skills, не вводить их только ради полноты таблицы.

**Обязательные ворота до кода:** схема/версии/capabilities и migration reader old v3 → новый vNext (старые v3 открываются read-only старым контрактом без скрытого превращения); source author contract; negative tests на spoofed owner, stale action, missing item/quest, invalid source grants. Existing v3 MUST remain importable.

### Пакет EXTRA-P2 — «Расширенная энциклопедия, богатые visuals, межсценовая история»

Добавлять после полного book→game E2E и real device QA: local private timeline диалогов с per-turn provenance, дополнительные фильтры/поиск, safe codex, optional pixel portraits/VisualRecipes, лёгкие анимации. Не делать эту опциональную роскошь входным требованием для обычной текстовой книги.

## 10. Согласование с главным roadmap

- **P0 full-book→v3:** выполняется сейчас; не задерживать новым schema и не переписывать главную программу.
- **P0 UI-P0:** завершённый небольшой read-only пакет может идти рядом с финальной проверкой книги; он заменяет старые текстовые простыни и не расширяет игровой контракт.
- **P0 NPC:** только дополнение к принятому actor-scoped контракту и social milestone, не параллельный движок.
- **P1 content/gameplay:** авторский BookEvidenceGraph / GameScenarioGraph, предметы/обязательства/условия/quests и поддерживающий vNext — одна цепочка, не набор декоративных UI.
- **P2+ visuals/AI/editor:** сохраняются в генеральном плане как опциональные компоненты; не получают приоритет над законченным базовым прохождением.
- **Принцип релизов:** связанные изменения = один функциональный PR + source/replay/schema/Dart/Python/Flutter acceptance. Внешний E6 и основной native могут работать в отдельных ветках, но зависят от одного versioned contract и проходят exact-head parity до merge.

## 11. Итоговое решение и источники

**Дизайн:** 3 неизменные игровые кнопки, вложенные модули только по наличию механик. **Данные:** только committed world и проверенный source. **Действия:** только авторизованный choice/typed effect. **Журнал:** действительные события и их последствия; задания, сведения и история реплик — отдельные смысловые виды. **NPC:** source-/character-ID-linked факты, направленные отношения и spoiler gates. **Совместимость:** v3 без сюрпризов, новые capabilities — только versioned vNext с writer/importer/save parity.

**Ближайший отчёт результата:** один UI-P0 acceptance set и настоящий E2E из книги, прежде чем переходить к GAME-P1.
