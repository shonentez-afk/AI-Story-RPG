# AI Story RPG — готовые Web-игры и выпуск на Яндекс Игры

**Дата решения:** 7 ноября 2026 года. **Статус:** исследованный технический план, ещё не реализация и не публикация. Нормативное дополнение к [единому генеральному плану](AI_STORY_RPG_COMPLETE_GAME_UNIFIED_SPEC_RU.md). Ветка внешнего генератора вправе менять только `tools/rpg_author/`, `tests/rpg_author/` и документы в этой области; **основные Flutter/Dart файлы пока только читаем**.

## 1. Принятое продуктовое решение

**Веб должен воспроизводить уже готовые игры, а не создавать RPG из книг.** Два независимых канала дистрибуции с одним игровым ядром:

**A — Яндекс Игры (приоритет публикации):** **один фиксированный, предварительно проверенный и разрешённый к публикации сюжет / один автономный HTML5-релиз**. Пользователь сразу видит титул и меню этой игры: «Продолжить», «Новая игра», «Настройки», при необходимости «Главы/Достижения». **Нет** библиотеки чужих игр, кнопок импорта FB2, .bworld и .bwsave, генератора, редактора или обращения к GLM/ChatGPT/другим интерактивным LLM API. Всё содержимое прошито в игровой дистрибутив, даже если внутренним форматом остаётся один верифицированный `game.bworld`.

**B — обычный собственный Web-плеер (опционально и позже):** один универсальный клиент только для **открытия уже созданных локальных `.bworld`**, без их генерации; выбор файла браузером, список импортированных игр, независимые сохранения для каждого. Размещать на собственном сайте после той же проверки Web runtime. Не включать режим загрузки чужих игр в Яндекс-издание и не использовать «универсальную библиотеку» как способ обхода модерации.

**Windows + Android остаются полными инструментами** для импорта книг, создания/редактирования/анализа игры по проектному roadmap. Web — только плеер. Основной проверенный движок, формат действий, идентификаторы NPC, replay, пиксели и косметический SkinPack используются повторно.

## 2. Критические требования Яндекс Игр — проверено по официальным документам 07.11.2026

1. **Интерактивный ИИ запрещён, заранее сгенерированные ИИ-материалы допустимы.** Полная история, диалоги, выборы, NPC-реакции и все допустимые исходы должны быть готовы ДО публикации. Онлайн GLM/ChatGPT-NPC и AI free-text action не включать. Механические проверки core/replay и ветвления без ИИ допускаются в принципе, но конкретную игру всё равно оценивает модерация. Официальные требования п.1.23: https://yandex.ru/dev/games/doc/ru/concepts/requirements
2. **ZIP размещения: до 100 МБ в распакованном виде**, один `index.html` в корне; пути без пробелов и кириллицы. Весь Flutter runtime/движок/шрифты/сцены/skin/HTML5/JS SDK включены в лимит. Поэтому процедурный pixel/art/skin без тяжёлых PNG и копий шрифтов — полезная архитектура. https://yandex.ru/dev/games/doc/ru/console/add-new-game
3. **Нужен официальный Yandex Games SDK**, `YaGames.init()`, корректный `ysdk.features.LoadingAPI.ready()` только после фактической готовности интерфейса, `GameplayAPI.start/stop` и обработка `game_api_pause/resume` при наличии соответствующей разметки. Гостевой запуск и сохранение прогресса без сторонней авторизации. https://yandex.ru/dev/games/doc/ru/sdk и https://yandex.ru/dev/games/doc/ru/sdk/sdk-game-events
4. **Облачное Player.setData ограничено 200 КБ на игрока**; `setData` не более 100 запросов за 5 минут, getPlayer тоже имеет лимиты. Не пытаться отправлять туда весь исходник книги/ZIP/крупный SQLite/Journals. Хранить версионированный компактный progress: game_id, archive_hash, branch/revision, committed event IDs или минимальный детерминированный snapshot, state/hash-chain head, settings; сначала проверить реальный размер на длинных играх. Для гостя нужен локальный safeStorage/бэкап и отказоустойчивый restore. https://yandex.ru/dev/games/doc/ru/sdk/sdk-player
5. **Нет дубликатов:** отдельные игры допускаются не просто за смену заголовка, скина, картинки/персонажа. Модерация оценивает core mechanic, объём и существенную уникальность содержания, дизайн, UI/UX; простые рескины одного шаблона могут отклонить. Если серия рассказов однотипна, рассмотреть **один сборник разных лицензированных историй** с выбором только ВСТРОЕННЫХ игр; это обновление/контент одного релиза, не импорт пользовательских файлов. https://yandex.ru/dev/games/doc/ru/requirements/3/6
6. **Без внешних логинов, магазинов и ссылок на сторонние ресурсы**, скрытых рекламных редиректов; интерфейс должен полноценно работать на заявленных мобильных и десктопных браузерах, быть responsive/без HTML page scroll, правильно переживать поворот, паузу, отключение фокуса, обновление страницы. https://yandex.ru/dev/games/doc/ru/concepts/requirements
7. **Монетизация:** если будет реклама, показывать только на естественных паузах (переход между актами, меню), а не во время чтения текста/выбора. На рекламный блок остановить gameplay, отключить игровой звук, затем корректно resume. Не делать обязательный rewarded ad для канонических концовок/основных диалогов. https://yandex.ru/dev/games/doc/ru/sdk/sdk-adv и https://yandex.ru/dev/games/doc/ru/sdk/sdk-events
8. **Авторские права:** опубликованный архив доступен аудитории, в отличие от приватного .bworld; перед export нужна независимая проверка прав на исходный текст, перевод, имена, иллюстрации, обложку и их адаптацию. Исторический оригинал сказки может быть общественным достоянием, но поздний русский перевод/издательская версия — не обязательно. Частные FB2 и приватные проверки по умолчанию НЕ публиковать. Никаких персональных файлов в GitHub Actions или игровой ZIP.

## 3. Почему не просто `flutter build web` от всего приложения

Прочитаны реальные файлы main 81fb75b77f11b8f82cafa1e7604afa9fe9bbb678:
- `apps/story_reader/lib/book_storage.dart` импортирует `dart:io`, Directory/File и `path_provider`;
- `apps/story_reader/lib/world_library_gateway.dart` импортирует `dart:io`, `dart:isolate` и использует native `BookworldCampaignStore.openPrivateDirectory`;
- `packages/campaign_manager/lib/campaign_manager.dart` импортирует `dart:io`, package `sqlite3` с нативным SQLite, WAL и файловой базой;
- `apps/story_reader/lib/ai_connection.dart` импортирует `dart:io` и `HttpClient` + secure OS key vault;
- `apps/story_reader/lib/book_import.dart` — парсер FB2/TXT в основном чистый Dart, но в Яндекс релизе импорт книги не нужен;
- `packages/story_core` и `story_runtime_adapter` — предпочтительная **общая детерминированная игровая логика**, без второго независимого браузерного game engine;
- `scene_dialogue_stage.dart`, `world_play_page.dart`, `game_panels.dart`, `reader_chrome.dart` — возможно переиспользовать read-only UI widgets через отдельный web entrypoint с platform-neutral gateway.

Официальные ограничения Flutter Web: нет `dart:io`, и обычные Dart isolates не поддерживаются в Web; conditional imports/platform adapters обязательны. https://docs.flutter.dev/platform-integration/web/faq

**Рекомендуемый будущий модуль основного репозитория:** `apps/story_web_player/` (название проектное) или отдельный `main_yandex.dart` + platform adapter. Не тащить туда анализ FB2, книгу-библиотеку, редактор NPC, GLM/secure key vault, SQLite native gateway. Загрузка только из заранее вшитого verified `game.bworld`, исполнение с уже имеющимся story_core; browser storage adapter от платформы. Для постоянного save применить компактный save/replay contract и синхронизацию Yandex SDK. Обязательно сохранить stable character_id, scene ID, source identity, вариант истории, trust/knowledge gates и полноценный журнал.

## 4. Схема готового релиза

Пример будущего потока (НЕ существующая CLI-команда):

```text
PRIVATE FB2 -> полный литературный/игровой анализ -> verified game.bworld + attribution
                                            |
                                            v
                             PUBLICATION RIGHTS / QA GATE
                                            |
                                            v
                  game-release manifest (game_id, title, locale, theme, hash)
                                            |
                                            v
              StandaloneWebPackager (Flutter Web + JS YandexSDK + embedded game)
                                            |
                                            v
                          yandex_game_<slug>_v1.zip
                                            |
                                            v
                      draft / SDK QA / moderation / publication
```

Внешний генератор должен делать **готовую игру и приватный пакет верификации**, но **право выпускать публичный ZIP только после явно подтверждённых прав и литературной приёмки**. Функциональный пакет standalone web release builder в основной программе выполняет выбранный и заранее версионированный build target, а не копирует чужой gameplay engine. На каждую публикацию меняются только content manifest, verified game, localized metadata и thematic visual recipes. **Никакой отдельной Flutter-ручной сборки с нуля на каждую книгу.**

**Минимальный экран отдельной игры:** титульная заставка/обложка, «Продолжить» (если есть save), «Начать», «Настройки», затем повествование+выборы+диалоги, нижняя строка «Герой / Предметы / Журнал», несколько настоящих концовок, титры/права; загрузка за разумное время. Удалить все названия «загрузить другую книгу», «подготовить RPG», API-ключи, «тестовый движок», режим черновой адаптации.

## 5. Сохранения, прогресс и безопасность

- Идентичность прогресса: `distribution_game_id + accepted_archive_sha256 + schema_version + campaign_id`; SQLite native не тащить напрямую в браузер. Загруженный progress должен пройти native-quality verify/replay всех committed effects и social/life gates прежде чем показывать UI.
- В облако Яндекса отправлять **малый проверяемый snapshot/log**, проверять 200 КБ hard limit и частоту API; debounce с гарантированной фиксацией критических переходов, без потери последнего действия при смене вкладки. При network failure — сохранение локально, повторная синхронизация позже, явное сообщение если облако недоступно.
- Гость играет сразу без Яндекс ID; cloud sync опционально с явным согласованным пользовательским действием. Не создавать forced auth.
- При апдейте игры оставлять валидность старых progress; если мир существенно изменён, отдельная проверенная migration/save policy или фиксирование content archive identity без незаметной переподмены истории.
- Никакого GLM API-key, приватных FB2/текстов и скрытого авторского редакторского досье в публичном ZIP. Вся публичная игровая проза/персонажи/ассеты являются контентом, доступным пользователю и технически извлекаемым из ZIP.
- Без исполнения кода из .bworld и без открытого импорта произвольных архивов на Яндекс. Только валидированный, вшитый заранее content.

## 6. Публикация: отдельная игра или сборник?

| Сценарий | Лучше | Почему |
| --- | --- | --- |
| Большое произведение с собственной историей/персонажами/ветвями, самостоятельный gameplay | **Один релиз одной игры** | Своя карточка, название, промоматериалы, версии и save |
| Новое название, но всё остальное — почти копия прошлой игры | **Не отдельный релиз** | Высокий риск отклонения как дубликата по пункту 3.6 |
| Несколько коротких однотипных сказок | **Одна игра-антология со встроенными историями** | Приятнее для пользователя, меньше риск множества однотипных релизов; нет произвольного импорта |
| Наш собственный сайт и пользовательские приватные .bworld | **Универсальный Web-плеер готовых игр** | Уже не Яндекс-витрина; можно позволить file picker без генератора/GLM |

Правило проекта: **каждая публикация — самостоятельный игровой опыт**, а не только новый skin/color. Но повторно используемый, проверенный deterministic core остаётся общим.

**Дополнение о настоящей прогулочной пиксельной RPG:** самостоятельный HTML5-релиз на Яндекс Играх может после отдельной реализации использовать **Flame top-down GameWidget** с процедурными локациями, WASD/стрелками и мобильным джойстиком, вместо текстового выбора на каждом шаге. Это лучше подходит для самостоятельного интерактивного издания по книге. **Но** все significant actions/NPC/item/world-state остаются в story_core; interactive AI по-прежнему исключён, контент заранее проверен и вшит, Yandex SDK/размер ZIP/save и права публикации не отменены. Полный новый план: [WALKABLE_PIXEL_RPG_FLAME_INTEGRATION_RU_2026-11-07.md](WALKABLE_PIXEL_RPG_FLAME_INTEGRATION_RU_2026-11-07.md). Экспорт не реализован; функциональный P2-WALK — после P0 и вместе с будущей проверенной Web-оболочкой.

## 7. Приёмка и этапы (не мешать основному P0)

**P0:** закончить первую настоящую приватную книгу→игру на Windows/Android, проверить NPC/item/quests/dialogues, варианты решений и сохранения; текущая внешняя E6f/Dart parity синтетическая, ещё не реальная игра.

**P1-Web design/prototype:** без вмешательства в основную разработку: создать в отдельной разрешённой ветке модуль `WebStandalonePlayer` для одной **синтетической** public-safe истории и однотитульный loader; без импортов/встроенного редактора/ИИ. Проверить web build, game core, Yandex SDK ready/start/stop и compact save.

**P2-Яндекс выпуск:** release ZIP validation, fixed embedded game, QA конкретного авторского контента, лицензионный gate, metadata, guest save/optional cloud, user reading UX, ad pauses, 100 МБ, модерация, update/migration policy. Собрать один функциональный пакет/PR, не дробить на экран/SDK-функцию.

**P2+ универсальный web-player на своём сайте:** после стабилизации общей web платформы; добавляется file picker уже готовых `.bworld` и проверка/индексирование в browser storage, **без** создания RPG из книг.

**Тестовая матрица:** первая загрузка и reload, guest/logged, изменения choice+memory+inventory+NPC life, 2 концовки, два сохраняемых прохождения, возвращение после закрытия рекламы/сворачивания/переключения вкладки, мобильный touch/portrait/landscape/scroll, desktop keyboard, 100/150% DPI, 200 КБ saves, отсутствие сети после инициализации core, отсутствие интерактивного ИИ, нет системной прокрутки HTML, отключение/повреждение cloud save, старое/новое содержимое. Сценическая пиксельная графика, скин и русские шрифты должны быть процедурными/локальными и недоступными для смены предметов/состояния.

**Состояние на сегодня:** архитектура и требования подтверждены по официальной документации, **код Web-Standalone и загрузка на Яндекс не выполнялись**. Этот документ не даёт права менять native main/apps/packages из внешней ветки; требуется отдельное явное поручение после P0.
