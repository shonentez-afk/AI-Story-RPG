## 0. Основное требование пользователя — БЕЗ обязательного редактора

> Пользователь передаёт книгу в ChatGPT. **Установленный навык ai-story-book-to-rpg должен создать целиком завершённую и проверенную игру и выдать ОДИН готовый к импорту файл game.bworld.** Пользователь открывает файл в AI Story RPG на Windows или Android и сразу играет. Редактор внутри приложения используется исключительно по желанию.

Игра создаётся **не частично**: навык обязан подготовить по всей выбранной книге персонажей, их характеры и мотивы, отношения, пределы знаний, офлайн-диалоги, предметы, характеристики, журнал, полные сюжетные переходы, условия, последствия, концовки, карты сцены и процедурные визуальные инструкции, а также правила допустимых свободных AI-взаимодействий. **Никаких действий «заполните профиль NPC», «дорисуйте фон», «допишите финал» после импорта.**

Отдельные рабочие файлы (source index, report, project_snapshot.zip, attribution) могут передаваться *дополнительно* для прозрачности и продолжения разработки. Для **обычного запуска** они не должны требоваться. Файл .bworld не содержит API-ключей или обязательной ссылки на облако.

**Offline-first:** всю сюжетную игру можно пройти без интернета и ИИ: заранее подготовленные тексты/диалоги, сюжетные выборы, интерфейс «Герой», «Предметы», «Журнал», сохранение, процедурная графика и лёгкая анимация работают локально. **Свободные новые реплики NPC через API** — дополнительное обогащение. Их нельзя гарантировать без подключения, согласия и поддерживаемого поставщика.

**Жёсткая формулировка готовности:** структурно верный ZIP ещё не «законченная игра». Нужны реальные завершённые маршруты, литературная и механическая проверка, проверяемые NPC/диалоги, соответствие изображения доступным знаниям, совместимость Python/Dart и фактические испытания. Если критические проверки провалены — не объявлять результат готовым.

## 1. Цели и независимые режимы

| Измерение | Варианты | Правило |
|---|---|---|
| **Сюжет** | CANON (авторский путь, исходный финал), ALTER_FATE (достоверные причинные альтернативы) | Не требовать искусственно 2 концовки от канона с одним исходным финалом. Для ALTER_FATE требовать действительно разные проходимые результаты |
| **Ввод** | CLASSIC_OFFLINE, AI_ASSISTED, AI_CONVERSATION | Один и тот же game state. ИИ интерпретирует речь и генерирует *речь*, но не создаёт незаконные игровые эффекты |
| **Оформление** | text, pixels_static, pixels_animated | Один и тот же сюжет, предметы, сохранения и события. Пиксели рисуются кодом, без обязательных PNG/ИИ-картинок |

Эти названия — будущие UX-режимы; не притворяться, что все они поддерживаются нынешним `.bworld v3`. В интерфейсе показывать только реально реализованные capability.

## 2. Единая техническая схема

    Файл книги FB2 / TXT (позже EPUB по отдельному этапу)
        |
        v
    [Навык ChatGPT + закреплённый Python tools/rpg_author из нашего GitHub]
        | A. Полный source-index (главы, UTF-16, SHA, точные цитаты)
        | B. Проверенный BookEvidenceGraph (события, сущности, знания, время)
        | C. GameScenarioGraph (герой, сцены, выборы, эффекты, финалы)
        | D. Профили всех важных NPC (голос, характер, мотивы, знания)
        | E. Полные сценарные диалоги и офлайн ответы
        | F. AI policies: SAY / LOOK / DO / INTERACT, допустимые действия
        | G. Visual Director: программные локации, персонажи, cues, анимация
        | H. Литературный + gameplay + NPC + dialogue + visual QA
        v
    [Версионированный компилятор + Python verifier + Dart importer]
        |
        v
      GAME.BWORLD   ← ОДИН самодостаточный игровой файл
        |
        v
    [Основное приложение AI Story RPG]
        | существующие story_engine + story_core + SQLite + gateway
        | Flutter диалоги, герой, вещи, журнал, сохранения
        | новый procedural pixel renderer, лёгкий scheduler анимаций
        | optional API разговоры через verified NPC knowledge
        | НЕОБЯЗАТЕЛЬНЫЙ встроенный редактор на Windows и Android

**Один источник фактов:** BookEvidenceGraph описывает, что доказано из книги; GameScenarioGraph — игровые факты и допустимые переходы; Visual/AI — их отображение и речевую форму. Событие внешнего ИИ или визуальной анимации не имеет права само создавать предметы, знания или записи игрового журнала.

| `ai_connection.dart` | GLM-4.7-Flash, opt-in, BYOK, HTTPS, secure storage | Сохранить инфраструктуру, расширять только по новому информированному согласию |
| `npc_knowledge_rulebook.dart` / NPC bridge | Source/approval-bound эффекты NPC knowledge | Переиспользовать точные семантические границы знаний |
| `tools/bookworld/private_rich_bookworld.py` + Dart importer | Строгая упаковка и импорт rich-v3 | Создать **новую явную версию** для дополнительных разделов; текущую не ломать |

**Факт о текущем формате:** .bworld v3 — ровно четыре ZIP_STORED записи: `manifest.json`, `scenario/blueprint.json`, `source/provenance.json`, `world.sqlite`. Строго проверяются пути, поля, хеши, SQLite. Нельзя незаметно добавить в v3 папку visuals/characters/AI: архив перестанет импортироваться. Поэтому **цель «один файл со всем» требует согласованного нового format_version, условно v4, с writer + Python verifier + Dart importer.**

**Разделение релизов:** пока новая версия не создана, установленный E6d может собирать проверенную **текстовую** rich v3, но нельзя обещать, что она автоматически содержит пиксельные сцены и свободные AI-NPC. Временные внешние JSON допустимы лишь для dev/QA, **не как окончательный обязательный пользовательский импорт**.

**Лицензионные ворота:** до прямого копирования кода — проверить конкретный LICENSE каждого upstream и всех использованных фрагментов, при MIT сохранить copyright/NOTICE. «README говорит MIT» не автоматически означает юридически проверенный дистрибутив. Для нашего проекта предпочтительна независимая Dart-реализация идей. Книжные права проверять на конкретном издании/переводе, а не только на авторстве оригинального произведения.

## 5. Обязанности НАВЫКА и ChatGPT: выпустить полный мир самому

Навык ai-story-book-to-rpg — **главный автор/координатор**, а не инструкции пользователю «сделайте персонажей». Он получает проверенную версию Python генератора **из нашего GitHub** и пишет структурированные данные по строгим схемам. Вся выдумка, маркировка адаптаций, QA и финальная компиляция проходят здесь **до** импорта в приложение.

### Полный pipeline будущей версии навыка

1. **Приём книги и настроек.** FB2/TXT сейчас; EPUB позже после реализации. Выбрать сюжет CANON/ALTER_FATE, героя, язык, визуальный режим. Если необязательные параметры не заданы, явно записать разумные defaults. Для облачного анализа книги нужно отдельное информированное согласие; частные книги никогда не публиковать.
2. **Версионированный bootstrap.** Навык загружает проверенный commit Python tools/rpg_author из нашего GitHub, сверяет SHA/doctor/contract. Приватные исходники, проекты, отчёты лежат вне публичного checkout. Без рабочей среды **не заявлять**, что файл собран.
3. **Прочитать ВСЮ книгу небольшими отрезками.** Сохранить original block/chapter/chunk, точные UTF-16 цитаты и source_fingerprint. Отделить факт повествования NARRATED, чью-то реплику REPORTED и вывод INFERRED.
4. **Единый литературный каталог.** Создать source-linked события, утверждения, действующих лиц, псевдонимы, места, предметы, цели, обещания, владение и знания; различать текстовый порядок и реальную хронологию. Никакого слияния NPC по одинаковому имени без подтверждённой связи.
5. **Независимый BookEvidenceGraph.** Узлы и связи: source quotes, happens_before, verified_causes, candidate_causes, knows_after, owns_after, located_at. У каждой спорной связи evidence/uncertainty. Сверить с уже имеющимися Dart narrative/evidence types.
6. **Цельная игра по всей книге.** Сцены, акты, выбор героя, задачи, предметы, знания, журнальные описания, условия, последствия, концовки. CANON не заменять искусственными развилками; ALTER_FATE создавать с реально разными маршрутами и пометками EXPLICIT_ADAPTATION. Завершённость сцены обязательна.
7. **Записать ВСЕ нужные NPC-карточки** (см. §6): identity, характер, цели, мотивация, отношения, эмоциональные состояния, манера речи, цитаты, knowledge_by_act/scene/state, неизвестное и запрет спойлеров, что NPC видел, визуальная идентичность, реакция на выборы. Для второстепенных персонажей допускаются краткие, но честные карточки.
8. **Выписать все обязательные диалоги.** Структурированные speaker_id и turn_id, оригинал/адаптация, текст реплики, допустимые ответы/вопросы, эмоции, действия и последствия. Создать полноценный offline fallback: API не нужен, чтобы завершить игру.
9. **Подготовить AI interaction affordances.** Для каждой сцены описать, кто виден/доступен, о чём можно говорить, что можно осмотреть и с чем взаимодействовать, какие естественные фразы относятся к **разрешённым** choice_id. Не превращать свободный текст в произвольный код/эффект.
10. **Автоматически спланировать пиксельные сцены.** Для всех важных мест/персонажей определить кодовый archetype, style/palette, seeded appearance, планы сцены, позиции, предметы, gestures и лёгкие animation cues; от неизвестных объектов требовать честный TEXT_ONLY/PARTIAL fallback, не выдумывать достоверный вид.
11. **Независимые проверки и исправления.** Пройти вторым отдельным литературным критиком мотивацию/хронологию/знания/логические последствия. Исполнить reachability/replay/диалоговые one-shot/предварительное знание, проверку NPC spoilers, visual coverage/unknown renderer opcode, prompt injection/privacy, consistency source/story/visual IDs. При правке инвалидация зависимых SHA/gates, повтор QA.
12. **Собрать ОДИН .bworld.** Писать только через проверенный writer поддерживаемой версии, архив, манифест, graph/NPC/dialogue/interaction/visual данные и QA fingerprints связаны хешами. Независимо проверить Python и Dart import, восстановить реальное прохождение по маршрутам и сохранения.
13. **Отдать пользователю.** Главный результат game.bworld; указать supported_app_min_version и status. Отдельно по желанию — project_snapshot.zip для продолжения другого чата и короткие отчёты с SHA. Редактор для завершения работы не требуется.

**Инструкция для будущего обновления навыка:** стадии 4–10 становятся обязательными при построении самодостаточной визуальной версии. В skill закрепить, какие входные и выходные schemas читает ИИ, требования к полноте, проверку синтаксиса/источников, независимую литературную оценку, автоматическую сборку/verify/replay, stop conditions и сохранение проектов. Не менять работающий pinned E6d до полной реализации новой pipeline и тестового acceptance gate.

### Статусы готовности различать обязательно

- **STRUCTURE_PASS**: архив, точные SHA/типы/трассируемые ссылки, SQLite, replay.
- **LITERARY_REVIEW_PASS**: полное покрытие выбранной книги, проверка смысла, идентичности, знаний и мотивов; литературная оценка не является математическим доказательством.
- **RUNTIME_PASS**: настоящий Dart importer, воспроизведение ветвей, диалогов и кадров, сохранения, тесты на Windows/Android.
- **USER_READY**: все применимые ворота закрыты, ограничения честно заявлены. Зелёный CI с фиктивной сказкой не доказывает реальную книгу; если физический E2E на устройстве не выполнен — это явно обозначенный остаточный риск, не заявленный PASS.


## 6. Какие ИМЕННО данные ИИ создаёт для персонажей заранее

Нужно различать три ID: **source_mention_group_id** (группа упоминаний), **reviewed_character_id** (литературно подтверждённая персона) и **world_actor_id** (участник игровых правил). Совпадение имени или внешнего вида не создаёт тождество. При каждой привязке хранить подтверждение из source graph и revision.

### Структура каждой полноценной карточки NPC

| Поле | Для чего оно нужно |
|---|---|
| Identity и aliases | Имя, титулы/прозвища, однозначный ID, статус неоднозначных персонажей, источниковые ссылки |
| Persona и speech style | Манера речи, темперамент, социальная роль, типичные выражения, эмоциональная окраска, **примеры собственных проверенных реплик** |
| Source-supported appearance | Внешность по точным цитатам; неподтверждённые детали отмечены как нейтральная **игровая стилизация**, а не канон |
| Goals/motives by act/scene | Зачем персонаж действует, что пытается получить, какие обещания/обязательства уже возникли, как цели меняются после подтверждённых событий |
| Relations | Отношения к другим verified characters, кто с кем знаком, что может помнить, отношения не выводятся автоматически из одного контакта |
| Knowledge timeline | Что **знает до** события, после какого подтверждённого choice/event может узнать новый факт, кто являлся свидетелем, что запрещено раскрывать заранее |
| Inventory / location / presence | Владение предметами и правдоподобное присутствие NPC по состояниям; персонаж не возникает в другом месте для ответа на вопрос |
| Dialogue script и topic coverage | Готовые офлайн реплики, допустимые вопросы, стартовая фраза, варианты отказа, одноразовые темы, answer scene/turn IDs, origin |
| AI contract | Что разрешено SAY/LOOK/DO/INTERACT, какие намерения маппятся на existing choice_id, какие темы неизвестны/запрещены, максимальный объём ответа |
| Visual recipe | Уникальная процедурная внешность, палитра, appearance seed, маски/пропорции/одежда, poses/emotions, допустимые жесты |
| Source provenance | Citation IDs для биографии/мотивации/знания, канон vs EXPLICIT_ADAPTATION, статус литературного ревью |

Это **обязательная работа навыка по всем персонажам, существенным для сюжета**. Профиль может быть коротким, если в исходнике мало данных; запрещено заполнять пустоты «уверенными» каноническими сведениями. Важно учитывать одновременно *собственную память NPC* и *изменения мира*: player utterance («я твой король») остаётся утверждением игрока, а не разрешением дать ключ.

### NPC memory (память после начала игры) — не часть исходной истины

Игра поставляется со **всеми начальными профилями внутри game.bworld**. Позже при общении сохраняются слова игрока, ответы NPC и краткие private conversation summaries, разделённые по campaign_id, world_hash, actor_id и актуальному scene/revision. Сведения помечаются PLAYER_CLAIM, NPC_REPLY, CONFIRMED_WORLD_EVENT; только последний тип может отражать verified мир. По умолчанию память разговора локальная, ограниченная, доступная для просмотра/очистки; её перенос между устройствами — отдельная проверяемая функция сохранений и политики приватности. Первичная game.bworld от этого не изменяется.

### Согласование с ЕДИНОЙ карточкой персонажа, реализуемой в основном приложении (2026-11-06)

**Источник решения пользователя:** в основном приложении разрабатывается единая полная карточка: **(1) личность** — постоянный `character_id`, имя, прозвища, роль, внешность, портрет; **(2) характер** — темперамент, мотивация, цели, манера речи; **(3) связи** — отношения по чужому `character_id`, а не по имени; **(4) знания** — известные NPC факты и события их приобретения; **(5) происхождение** — точная цитата книги, предположение ИИ или игровая выдумка.

**Окончательный принцип интеграции:** это **одна общая карточка**, принадлежащая основному приложению и его сериализуемому контракту. Любой `npc_profile_v1`/пример JSON в настоящем документе — лишь черновик, который будет **адаптирован под принятый формат основной карточки**, а НЕ второй независимый формат в Python/навыке. Нельзя вводить внешнее поле или перечисление статуса, не сверив его с действительно принятым Dart schema/writer/importer/тестами. До такого контракта допускаются отдельные **временные приватные черновики** только с явным review и mapping.

**Обязательные правила:**

- `character_id` назначается один раз в рамках готового игрового мира, не выводится каждый раз из имени или случайного порядка упоминаний; разные версии одной истории сохраняют стабильные ID только после подтверждённой identity mapping. Существующие `source_mention_group_id` и `world_actor_id` нельзя считать синонимами. Для их связи нужен строгий reviewed mapping с source-fingerprint/edition/revision и диагностикой конфликтов.
- Для каждой роли навык должен сам создать **полностью заполненную настолько, насколько позволяет книга** карточку: подтверждённые поля, честно отмеченные неопределённости и отдельные EXPLICIT_ADAPTATION сведения. Нет обязательного ручного этапа «заполнить персонажей» перед выдачей `.bworld`.
- Отношения хранятся через IDs обоих персонажей и проверяемые виды связи, направление, условия/события изменения, происхождение и степень доказанности. Запрет dangling refs, self-contradiction, произвольного совпадения имени. Одинаковые `display_name` разрешены у разных героев при разных IDs.
- Знание NPC — не просто список фактов: требуется связать получение/утрату (при поддержке) с **проверенными игровыми событиями и условиями ветки**, возможностью услышать/увидеть, игровыми фактами и ревизией. Не показывать знание будущей главы или другой ветки. `PLAYER_CLAIM` хранится как чья-то реплика и не превращается сам собой в `CONFIRMED_WORLD_FACT`.
- Происхождение — **на уровне каждого поля/отношения/знания и реплики**, а не общая сноска на карточку: `BOOK_QUOTE` с точной цитатой и source span; `AI_INFERENCE` с ограниченной уверенностью/основанием; `GAME_FICTION` как явная адаптация. Точные enum/идентификаторы принять только из будущего общего schema, не продавливать названия из документа в Dart. Проверка статуса не равна литературной истинности.
- **Портрет:** кодовая procedural-пиксельная внешность должна быть основным переносимым вариантом, тот же `character_id`/appearance seed должен использоваться в диалогах и сценах. Локальный вручную выбранный PNG остаётся **опциональным** пользовательским оформлением, не требуется навыку, не генерируется через модель изображений. Нельзя путать имя в текущем `DialogueStage` с подтверждённой личностью.
- При будущем AI-диалоге передавать модели только **доказанные доступные NPC знания** и его допустимую persona, а не всё знание книги/все карточки. Связь подписанной реплики с `character_id`/будущим `turn_id` формируется и проверяется отдельно от текста и не угадывается по совпавшей строке имени.

**Живая проверка main:** commit `4f94fc3d2dcdba3258ba5418faff37fc366b4ff9` после [PR #125](https://github.com/shonentez-afk/AI-Story-RPG/pull/125) (проверка говорящих по исходным упоминаниям, неоднозначных имён, поздних спойлеров). В принятом main есть `source_character_dossiers.dart`, `npc_editorial_notebook.dart`, `npc_knowledge_rulebook.dart`, `source_locked_dialogue_speaker_audit.dart`. **Проверенно целостной новой карточки с перечисленными 5 секциями там пока нет**, пользователь сообщает, что её разрабатывают параллельно; в будущих чатах перед адаптацией внешнего генератора повторно проверить её реальную схему и PR. PR #125 НЕ доказывает соответствие конкретной реплики знанию NPC; его аудит специально отличает упоминание от знания.

## 7. Свободные разговоры и действия — как ИИ не сломает сюжет

**Решение:** свободный ввод не ограничивать кнопками диалога. Он доступен для беседы, исследования, попытки действия и социального взаимодействия. Но все фактические последствия остаются строго контролируемыми. Это сочетает идею Convai (NPC objective/section), AI Town (память), AI Dungeon (Say/Do/context cards) и Rasa CALM (LLM intent + deterministic flow).

| Режим | Пример | Допустимый результат |
|---|---|---|
| SAY | «Почему ты здесь? Чего хочешь?» | Ответ NPC в собственном стиле с учётом *его* проверенных знаний; никакого автоматического изменения мира |
| LOOK | «Что лежит у берега?» | Описание только видимых объектов из snapshot; может быть офлайн или с AI-стилизацией, но без новых фактов/спойлеров |
| DO | «Попробую достать мяч» | Offline matcher / AI предложит уже разрешённый choice; **только после подтверждения** исполняется WorldLibraryGateway.choose |
| INTERACT | «Давай обменяем мяч на обещание» | Персонаж произносит реакцию; возможное игровое соглашение — лишь если есть допустимый проверенный сценарный выбор |
| STORY/IMPROVISE | «Изобрету новый сюжет, которого нет в книге» | **Не входит в основную совместимую игру**; будущий отдельный эксперимент с новым reviewed graph и audit. Не маскировать самодельные события под канон |

### Строгая последовательность одного API-запроса

    Написано игроком -> SAY / LOOK / DO / INTERACT
        -> прочитать текущий verified world snapshot
        -> проверить, что NPC/предмет реально доступен в сцене
        -> выбрать ТОЛЬКО knowledge/visibility, доступные этому NPC/игроку
        -> извлечь релевантные persona/source-safe facts/recent local memory
        -> показать состав передаваемых в облако данных и получить отдельное согласие
        -> вызвать Z.ai через существующий защищённый transport
        -> проверить bounded typed reply (не выполнять модельный код)
            SAY: короткая NPC реплика + optional emotion/gesture
            LOOK: только обоснованное описание, no hidden knowledge
            DO/INTERACT: candidate existing enabled choice_id или null
        -> при игровом эффекте перечитать свежую scene+revision+fingerprint
        -> подтвердить действие у игрока
        -> существующий gateway + story_core + SQLite commit
        -> при успехе обновить Герой/Предметы/Журнал и только затем visual cue

**Никаких новых игровых эффектов от модели.** ИИ не вправе возвращать исполняемые grant_item, learn_fact, set_flag, next_scene, event_hash, arbitrary code или диктовать новые условия. Для NPC «я дам тебе ключ» — *слова*, а не предмет. Если по подтверждённому сценарию нельзя передать ключ, ключ в инвентаре не появится. Unknown choice/disabled choice/stale/duplicate → no commit и no acquisition animation.

**Литературная безопасность:** фильтрация входного контекста по доступным знаниям, времени и границам сцены обязательна. Даже это не даёт математической гарантии, что LLM не галлюцинирует: проверять возможные спойлеры и неустановленные факты, использовать ограниченные ответы/«не знаю», предоставлять запись о том, что реплика импровизированная. Не загружать целую книгу или все NPC secrets в один prompt. Character Card V2 используется только как идея persona; arbitrary system_prompt из файла/книги/диалогов считается недоверенными данными.

**Приватность API:** уже есть opt-in BYOK Z.ai GLM-4.7-Flash, ключ хранится в OS-protected FlutterSecureStorage. Текущая отправка AI advisor включает *только* игроковый ввод и видимые названия разрешённых действий. Новое использование persona/scene/knowledge/памяти требует **нового явного согласия на точный payload**, а не скрытого расширения существующего. Ограничения размера/токенов/стоимости, HTTPS allowlisted endpoint, TLS, повторы только для утверждённых 429/5xx/408/network, отмена, privacy controls и отсутствие секретов в логах. Не повторять игровой commit при сетевой неопределённости — перечитать журнал. Нет API = полная офлайн игра по готовым сценарным репликам.

**Ожидаемый структурный ответ** (проектный пример, не runtime contract текущего приложения):

```json
{
  "format": "npc_reply_v1",
  "scene_id": "pond_meeting",
  "revision": 3,
  "npc_id": "frog",
  "kind": "SAY",
  "reply": "О том, чего я не видел, я судить не могу.",
  "emotion": "neutral",
  "gesture": "turn",
  "proposed_choice_id": null
}
```

Выбор эмоции не меняет отношения/flags. Любые значения должны проверяться по allowlist, фактическому состоянию и длине. Изменение сцены отменяет устаревший ответ. Сохранение разговора отдельно от подтверждённого replay/game history.

## 8. Процедурные пиксели и лёгкая анимация — полностью программные

**Никакой нейросетевой генерации PNG, предварительных spritesheets или картинки как входа в пиксельный редактор.** Генератор не пишет произвольные исполняемые Dart/Python scripts для каждой книги. Он выдаёт разрешённый recipe с параметрами; один проверенный Dart renderer воспроизводит.

**Visual Director в Python:** выбирает по исходным событиям environment archetype (лес, пруд, замок, дом, улица, комната, дорога, город и расширяемые жанры), полигональную/пиксельную композицию, список объектов, палитру, время суток/погоду, устойчивые seeds персонажей, positions/poses, только разрешённые actions, потенциальные UI cues. Если книга не доказывает деталь, использовать нейтральный стиль с маркировкой EXPLICIT_ADAPTATION/UNSPECIFIED, не считать выдуманное каноном.

**Dart Pixel Renderer:** пиксели — целочисленные геометрические примитивы, маски, слои, оттенки и детерминированные seeded-вариации. Начать с Flutter CustomPainter / Canvas и логической области порядка 320×180 с nearest-neighbor. Один персонаж стабилен при загрузке и в разных сценах: seed вычислять из versioned SHA(source_fingerprint + reviewed_character_id + style_version), а не из нестабильного hashCode. Фоновая геометрия/повторяемые элементы кэшируются в памяти (это не подготовленные PNG файлы), группы примитивов рисуются эффективно.

**Лёгкие движения:** idle, blink, talk, turn, short_walk, appear, disappear, give, react, water_ripple, rain. Каждый cue — ограниченный opcode + duration + actor/turn/choice ID. Никакой физики, pathfinding, произвольных шейдеров, бесконечного model-generated animation code. После dialogue_turn — жест говорящего. После confirmed, nonduplicate choice — визуальный эффект. При reload — stable current scene frame, без повторной анимации получения вещей. При выключенных анимациях/reduced motion — статичный кадр, без игрового изменения.

**Three display modes:** text — вообще без render loop; pixels_static — готовая композиция; pixels_animated — композиция + cosmetic cues. Режим переключается в любой момент без изменения revision, inventory, journal и save. При ошибке рисунка/недоступном archetype — явный текстовый fallback, без падения игры и без демонстрации скрытых предметов. На первом полном доказательстве: пруд, принцесса, лягушонок, золотой мяч, две ветви и диалог — все рисуется **кодом** и перезапускается одинаково на Windows/Android.


## 9. Формат одного ГОТОВОГО .bworld: целевая новая версия

**Текущий v3 не подходит для хранения полного набора данных** из §5–8: его пути/JSON жестко фиксированы. Решение — явное версионирование **BookWorld v4 (условное проектное название, ещё не реализовано)**, параллельно сохраняя импорт старых v3. Не менять v3 скрыто и не навязывать пользователю внешние JSON.

### Проект состава одного архива (будущие пути; не действующий API)

```text
game.bworld
├── manifest.json
│   format_version, capabilities, min_app_version, renderer_version,
│   schema_hashes, hashes/sizes per member, provenance flags
├── scenario/blueprint.json
│   все игровые сцены/выборы/условия/эффекты/режимы/концовки
├── source/provenance.json
│   source fingerprint, rights, scene origin, citation IDs, AI attribution
├── world.sqlite
│   проверенная основа игры и данные, которые уже требует engine
├── story/book_graph.json
│   source-linked события/claims/relations без обязательного полного FB2
├── story/characters.json
│   полные карточки и подтверждённые знания всех нужных NPC
├── story/dialogues.json
│   готовые офлайн линии, speaker_id/turn_id, вопросы, варианты ответов
├── story/interactions.json
│   presence/visibility, SAY/LOOK/DO/INTERACT, mapping to enabled choices
├── story/ai_policies.json
│   ограничения scope, persona/knowledge/allowed actions, privacy metadata
├── visuals/recipes.json
│   процедурные актёры, декорации, seeds, палитры, poses, cues, fallback
└── quality/report.json
    проверенные версии тестов/охват, ссылки на ревью, оставшиеся риски
```

**Строгие принципы:**
- Всё обязательное для игры уже внутри ZIP. **Нет** готовых AI PNG, внешнего обязательного JSON, URL, API-key, shell/Python/JS/Dart-кода, динамических shaders, вредоносных данных.
- Саму исходную FB2/TXT книгу не помещать автоматически целиком. В игровом архиве компактные проверенные факты/цитатные ссылки и допустимые для приватной адаптации фрагменты; исходник хранится отдельно в закрытом snapshot автора. Исполнять готовую игру можно и без повторной загрузки книги.
- Манифест строго фиксирует формат, режимы, полные списки членов/хеши/размеры, source/story/blueprint hashes, min supported app/renderer version. Два независимых валидатора **Python и Dart** одинаково отбрасывают неизвестные/опасные записи и неканонический JSON.
- Не считать заполняемый генератором quality/report.json математическим доказательством художественного качества: реальные tests/replay/reading review независимы от этого поля.
- Legacy v3 продолжает открываться и играть по нынешним правилам. Новый v4 открывает **только совместимый новый importer**, иначе приложение понятно сообщает «нужна новая версия» и не повреждает мир/сохранения.
- Python и Dart используют единый spec с проверкой синхронности; формат реплик и визуальные опкоды имеют числовые/string limits. Проверить архив на zip-slip/duplicate entries/symlink/zip bomb, большое количество объектов, переполнение таймлайна, неподдерживаемый opcode и злоупотребление JSON.

**Поэтапное ограничение:** до реализации v4 навык честно выдаёт только **поддерживаемую текстовую rich-v3 игру**, а разработка визуальных sidecar остаётся внутренним испытанием. Не выдавать несколько обязательных файлов вместо обещанного одного game.bworld как окончательный продукт. Единственный пользовательский файл с динамическими NPC, диалогами и пикселями — приёмочное требование новой версии, не сегодняшняя возможность.

**Переходы сохранений:** уже существующий campaign_manager привязывает сохранение к конкретному world/archive hash. Даже чисто визуальная новая версия ZIP получит новый archive hash. Редактор должен сохранять оригинал и старые кампании, объяснять изменение привязки и не переиспользовать save тайно; локальный preview косметики может быть overlay без изменения базового архива. Совместимый перенос возможен только после отдельной проверки версии игрового blueprint и event log, без опасного автослияния.

## 10. Встроенный редактор: что делает игрок ПОСЛЕ готовой игры

Редактор входит **в то же приложение** на Windows и Android; не отдельный desktop tool и не обязательный шаг генерации. В обычном режиме: «Книга → Играть». Кнопка «Редактор игры» ведёт в расширенное рабочее пространство.

| Экран | Что показывает / меняет |
|---|---|
| **Граф книги** | Литературные события, персонажи, доказательства, что из оригинала/догадки, переход к цитате, мировая хронология |
| **Граф сюжета** | Акты, игровые узлы, choice, условия/эффекты, флаги и финалы, быстрый playtest и ошибка ветки |
| **Персонажи** | Профили, source mapping, характер, манера речи, цели по актам, отношения, знания и запретные темы, allowed intents |
| **Диалоги и AI** | Поочерёдные линии и speaker_id/turn_id, ответы NPC, доступные вопросы, тест «до/после знания», подготовленные примеры, LLM context preview, отказ/неизвестно |
| **Пиксельные сцены** | Программный предпросмотр, палитры, генераторы форм, привязка предметов, положение персонажей и слои |
| **Анимации** | Простая последовательность scene_enter/dialogue_turn/choice_committed → gesture, скорость, reduced motion |
| **Проверка/Экспорт** | Ошибки и цитаты, невоспроизводимые события, достигнутые маршруты, приватность, сборка нового файла game.bworld |

**Windows:** canvas и блок-схема, панель источников, свойства, preview, timeline. **Android:** адаптивные вкладки, поиск, простые исправления и отдельный полноэкранный граф; не пытаться уместить ПК layout на телефоне 320–360 dp.

**Единый источник данных:** элементы редактора меняют *проект* по тем же схемам, которые читает навык, а не отдельную копию правил; граф/логика остаются в game/authoring model. Drag узла на диаграмме — только визуальный layout; не меняет choice. Изменённое условие, знание, связь, реплика или принадлежность — новая ревизия, инвалидация зависимых QA и повторная компиляция. Косметическая поза/цвет — только visual validation, но при **экспорте нового архива** всё равно новый archive SHA.

**Если требуется перепроверить редактируемый канон по книге:** game.bworld содержит проверенные ссылки и сведения, **но не всю книгу**. Для глубокой правки source truth редактор должен запросить исходный FB2/TXT или приватный project_snapshot; без них допускается правка явно отмеченной GAME_FICTION/визуального представления, но нельзя ложно утверждать, что новая версия получила новый литературный source audit. Пользователь не должен предоставлять исходник для простой правки цвета/положения/сцены.

**Выбор Flutter graph library:** сначала имеющийся draft_scene_graph_overview и Mermaid export; затем измерить Vyuh Node Flow vs node_flow на 100/500/1000 узлах на Windows/Android, выбрать один, сохранить производительность и собственные смысловые validators. Вся программная логика изображения работает и без редактора.

## 11. Интеграция с основным приложением и пример выполнения события

### 11.1 Основной движок НЕ заменяем

1. Импортёр v4 проверяет БЕЗ исполнения чужого кода игровой package и все разделы.
2. Нынешний story_engine продолжает навигацию; story_core определяет условия и эффекты; story_runtime_adapter сверяет обе системы; campaign_manager пишет SQLite и replay.
3. WorldLibraryGateway выдаёт уже проверенное GameView + **read-only** opaque IDs/знания/присутствие NPC + last confirmed choice/event details. Обязательно исключить возможность UI mutation world state.
4. DialogueStage использует предзаписанные line/speaker IDs. NPCConversationController может предложить дополнительную AI-реплику, но не меняет мир и не ломает скриптовую очередь.
5. VisualSceneController читает сцену и доступные факты, строит пиксельный frame; CosmeticScheduler получает confirmed event/visible turn и запускает разрешённый cue.
6. Кнопка выбора/свободное действие — только через проверенный gateway + fresh revision. При denial/duplicate/stale → не играть acquisition cue и не менять предметы/журнал.
7. При перезапуске игровой state восстанавливается из replay, а визуальная композиция строится из same deterministic recipe; прошедшая ранее «передача предмета» не исполняется повторно.

### 11.2 Сценарий «принцесса и лягушонок»

**Подготовка навыком:** источник описывает пруд, лягушонка, принцессу, мяч, диалоги. Навык связывает quote IDs, создаёт literarily-reviewed scene/character/thing IDs, пишет NPC цель и пределы знаний, готовые офлайн реплики; программный recipe задаёт пруд, героев, мяч и короткое появление из воды. Навык заранее создаёт доступные choice IDs и последствия. Ничего не просит рисовать/дописывать пользователю.

**Прохождение без ИИ:** игрок видит процедурную сцену и готовый диалог, делает выбор, story_core проверяет/коммитит, пиксельный player лишь показывает реакцию, инвентарь/журнал меняются от game state, закрытие/открытие возвращает ту же историю.

**Прохождение с ИИ:** игрок пишет «А если я скажу, что верну обещание завтра?»; система выбирает присутствующего NPC, передаёт только разрешённый контекст, NPC отвечает своим стилем в рамках знаний. Если NPC произнёс обещание дать предмет — это ещё **не** grant_item. Для настоящего перехода требуется допустимый choice и успешный commit. Если действия нет, NPC может отвечать текстом или предложить предусмотренные варианты, но сценарий не переписывается.

**Редактирование:** пользователь позже открывает редактор, меняет положение пруда/цвет героев или реплику, запускает preview, при экспорте получает новый проверенный файл. Старое прохождение/архив не переписываются скрыто.

## 12. Где будет код — целевые границы

**Внешний генератор / навык** (поэтапные имена модулей, этих файлов ещё нет):
- `tools/rpg_author/book_graph.py`: source-lock и единые события/relations.
- `tools/rpg_author/npc_author.py`: persona, цели, knowledge-by-scene, example dialogues, AI policies.
- `tools/rpg_author/dialogue_author.py`: полные офлайн реплики, speakers/turn IDs, QA всех интерактивных тем.
- `tools/rpg_author/scene_interactions.py`: персонажи, объекты, видимость, intents/choice mapping.
- `tools/rpg_author/visual_director.py`: программатические рецепты всех доступных сцен.
- `tools/rpg_author/finalize.py`: одна команда всех совместимых QA/replay/packaging tests и отчётов.
- `schemas/rpg_author/*`: версии строгих JSON schemas; Python vs Dart parity.

**Основное приложение** (read-only до отдельного разрешения на изменения):
- `packages/bookworld_format/`: новый строгий importer v4, старый v3 сохраняется.
- Новый чистый Dart пакет `packages/procedural_scene_core/` для geometry/seed/poses/validators, без зависимостей от SQLite и game core.
- `apps/story_reader/`: `ProceduralSceneWidget`, `PixelPainter`, `VisualSceneController` и `NpcConversationController` как UI/adapters; внутри прежнего интерфейса герой/предметы/журнал.
- `apps/story_reader/`: `GameEditorPage` — **необязательный** расширенный редактор с теми же схемами.
- `tools/bookworld/`: явно новый writer/verifier целевого package, не «подправленный» v3.

**Установленный навык:** после завершения и реального тестирования новой версии генератора обновить pinned commit, инструкции стадий из §5, QA gates, snapshot/restore и критерии выдачи. **Не обновлять pin сейчас только из-за документации**: иначе можно получить несовместимость и ложный статус готовности.

## 13. Приёмка на практике: без «мы всё сделали» после одного зелёного CI

| Проверка | Критерий PASS |
|---|---|
| Весь источник | Проанализированы все индексируемые главы, exact UTF-16 ссылки/цитаты, не потеряны основные персонажи/события, unresolved вынесены отдельно |
| Сюжет | Проходимые и содержательно законченные ветви, корректные терминалы/условия/предметы, CANON не подменён альтернативой; ALTER_FATE — реально разные допустимые финалы |
| Герой/предметы/журнал | Реальные typed effects отображаются, инвентарь не заполняется фиктивными предметами, журнал проверяется replay |
| NPC | Профили ВСЕХ нужных действующих лиц, нет выдачи secret до события, место/знания/отношения согласованы, исходные цитаты и GAME_FICTION различимы |
| Диалоги | Все обязательные offline реплики и вопросы подписаны speaker/turn IDs, доступны в нужное время, one-shot и requires_fact проверены, пропущенных тем нет |
| AI | Без API проход возможен; с API restricted context и consent, unknown choice/маскировка ключа/spoiler injection не дают world effect; retry/429/timeout/cancel протестированы |
| Пиксели | Обязательные сцены программно воспроизводятся без PNG/сети, actor appearance seed стабилен, motion optional/reduced, никаких визуальных спойлеров |
| Формат | Один .bworld принимают Python verifier и Dart importer, всех членов и JSON схемы/hashes достаточно, недопустимые данные отклоняются, старый v3 продолжает импортироваться |
| Сохранения | Два и более маршрута, restore после закрытия во время жеста, independent campaigns, portable saves без задвоенных действий |
| Устройства | Важно отдельно проверять настоящий Windows и Android UI/performance/память/клавиатуру/scale, а не только сборку APK и synthetic widgets |
| Конфиденциальность | API off by default, книги/ключи/диалоги/цитаты не опубликованы на GitHub, источниковые права подтверждены для приватной адаптации |
| Обновление навыка | Bootstrap pinned version, full runbook, tests и автоматические snapshots/передача; текущий временный pin E6d не сбрасывается |

**Отрицательные обязательные сценарии:** недоступный NPC отвечает знанием будущей главы; модель выдаёт несуществующий choice; игрок убеждает NPC «дай ключ» без правила; stale/duplicate POST; подмена archive hash; неизвестный visual opcode; enorme layers/ZIP; сломанный JSON; потерянный answer topic; отключение сети в середине ответа; смешение памяти двух кампаний; неоднозначное совпадение одноимённых персонажей; перенос новой редакции поверх старого сохранения; внезапное закрытие в середине анимации.

**Содержательный аспект:** автоматическая проверка JSON/хешей не гарантирует художественного качества или стопроцентной правдивости произвольного LLM текста. На неоднозначных источниках нужен независимый смысловой аудит и честные недоказанные области. Если пользователь требует «полностью пиксельную книгу», покрытие ключевых сцен нельзя объявлять PASS при неоговорённом тексте вместо графики.

## 14. Реальный порядок реализации — сначала готовая игра, потом её редактор

| Приоритет | Результат | Что не блокирует |
|---|---|---|
| **P0 — ближайшее** | Закрыть текущие задачи внешнего E6e и main full-book/literary/structured dialogue gates; проверить **готовую текстовую rich-v3 игру** на «Короле-лягушонке» и второй книге; два маршрута и offline Windows/Android | Графический редактор, AI NPC, пиксели |
| **P1** | Навык автоматически создаёт единый BookEvidenceGraph, полные NPC cards, готовые offline диалоги, interactions/visual plans и строгий QA; проверка на синтетических и приватных настоящих историях | Ручной редактор |
| **P2** | Новый один self-contained .bworld (условно v4) с Python writer/verifier + Dart importer и Canvas procedural renderer, три display modes и короткие анимации. **Готовую визуальную игру можно импортировать сразу** | Сложные AI диалоги, редактор |
| **P3** | BYOK AI_NPC SAY/LOOK/DO/INTERACT и отдельная локальная conversation memory, contexts/consent/action gate; **без изменения offline полноты** | Случайная генерация новых ветвей |
| **P4** | Необязательный встроенный Windows/Android редактор графов, персонажей, диалогов, внешности и анимаций, QA и экспорт новой версии | Основной запуск готовой игры |
| **P5 при спросе** | Больше жанровых форм и лёгких анимаций, Flame при измеренной необходимости, офлайн LLM и отдельный экспериментальный проверяемый Story/Improvisation | Базовый функционал |

**Уточнение:** P2/P3 могут идти параллельно при согласовании одних ID/schema, но **нельзя** опять затягивать главную цель «передал книгу — получил завершённую игру» ради бесконечного нового редактора. Любой этап принимается только после функционального результата, не после написания ADR.

## 15. Неприкосновенные решения и ограничения

1. **Единственный обязательный выход навыка для игрока — один game.bworld.** Дополнительные отчёты/архив проекта — по желанию, не нужны для импорта.
2. **Все нужные NPC, сценарии, диалоги, факты, предметы, визуальные сцены/анимации навык создаёт заранее сам.** Редактор не используется для обязательного заполнения пробелов.
3. **Картинки не генерируются и не скачиваются:** пиксельные фигуры строятся кодом по рецепту; никакого обязательного PNG.
4. **ИИ не меняет игровой мир:** SAY/LOOK — языковая форма/наблюдение; DO/INTERACT → только существующий проверенный choice и успешный commit.
5. BookEvidenceGraph ≠ GameScenarioGraph ≠ Presentation; NPC память о словах ≠ подтверждённые знания; original vs EXPLICIT_ADAPTATION помечены.
6. Не дублировать game engine, не ломать current v3/SQLite, не хранить API ключи в файлах игры.
7. Main/app/packages/bookworld/CI в рамках этой внешней ветки **только чтение** до нового прямого разрешения. Установленный E6d skill pin не меняется без протестированной новой версии.
8. Пользовательских старых E5 архивов нет: не придумывать обязательную миграцию, не тратить время на отсутствующую базу.
9. Приватные книги, собственные переводы, пользовательские реплики, токены и любые персональные данные не публиковать в public GitHub/release/CI artifacts.
10. Не выдавать прочтение чужой документации за фактическую работоспособность в нашей игре; каждое приложение/renderer/AI/API пройти реальным end-to-end тестом.
