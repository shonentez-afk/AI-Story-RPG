# AI Story RPG — собственный скин под каждую книгу (UI + пиксельные сцены)

**7 ноября 2026. План, не готовый код.** Нормативное приложение к [генеральному плану](AI_STORY_RPG_COMPLETE_GAME_UNIFIED_SPEC_RU.md), разделам 8 и 9. Приоритет P2 вместе с процедурной пиксельной графикой, но не вместо завершения P0 «полная книга → готовая RPG».


> **Проверенный GitHub-анализ источников (7 ноября 2026):** [GITHUB_DYNAMIC_SKIN_SOURCE_REVIEW_RU_2026-11-07.md](GITHUB_DYNAMIC_SKIN_SOURCE_REVIEW_RU_2026-11-07.md). Выбраны конкретные файлы и модели: game-hud (12 скинов, общие токены), Flame (NineTileBox), Material Color Utilities (Dart-палитра), PixelForge (JSON→pixel, лицензия кода ещё не подтверждена), LovecraftUI (процедурные фактуры), BlockUI (5 тем/доступность, **конфликт корневой Apache-2.0 и пакетной MIT лицензий**), Godot Theme, Ren'Py, NES.css и Pixel UI Fantasy (CC BY). Фактический код из других репозиториев не копирован и не подключён. Это **технический реестр идей**, не CI-проверка готового скина.

## 1. Конечный результат

Пользователь передаёт книгу. Генератор анализирует её тематику, создаёт цельный визуальный стиль и применяет его не только к сценам, но и к **всему интерфейсу**: экрану текста, диалогов, портретам и именным табличкам, иконкам, кнопкам, главному меню, заголовкам, Герою, Предметам, Журналу, экранам сохранения, загрузки и концовки. Всё работает **офлайн** в одном готовом game.bworld на Windows и Android, без отдельной сборки приложения.

**У каждого произведения свой визуальный язык, но один работающий движок.** Скин не меняет GameScenarioGraph, знания NPC, события, инвентарь, условия выбора, журнал или сейвы. При открытии той же книги стиль остаётся стабильным: визуальная уникальность между книгами не означает хаотичное изменение оформления при каждом запуске. Явное «Сгенерировать другой вариант» позже может сменить style_seed, не меняя сюжет.

Примеры направления, не литературного канона:
- «Король-лягушонок»: пергамент, лесной изумруд, мягкая позолота, орнамент водяных лилий, иллюминированная рамка текста;
- детектив: досье/бумага, тёмные чернила, следы печатной машинки в заголовках, иконки улик;
- киберпанк: графит, холодный неон, строго ограниченные HUD-рамки, пиктограммы приборов;
- морское приключение: карты, компас, канаты, сине-песочные поверхности.

Не копировать готовые чужие UI, логотипы и обложки; недоказанные детали считать художественной стилизацией, не SOURCE_PASSAGE.

## 2. Архитектура (один согласованный арт-директор)

1. **BookEvidenceGraph:** темы, эпохи, места, настроение и характерные визуальные образы из всей книги; для каждого — категория SOURCE_PASSAGE/INFERRED/USER_STYLE_CHOICE. Не включать в скин скрытые сюжетные факты и секреты.
2. **VisualStyleDirector:** один Style Bible на книгу — 2–4 базовых цвета, нейтральные/контрастные цвета текста, материалы, пиксельная геометрия, орнамент, типографические роли, плотность украшений. **Отсюда же** формируются visual scenes, чтобы персонаж и UI не жили в разных стилях.
3. **SkinRecipeComposer:** строго ограниченный data-only JSON с палитрой, рамками, типами кнопок, форматами panels, заранее разрешёнными иконками и стабильным style_seed на основе source_fingerprint + style_revision + renderer_version. Без модели, генерирующей Flutter/Dart/JS-код.
4. **Flutter SkinRenderer:** один переиспользуемый движок тем на базе ThemeExtension, существующих виджетов и проверенного CustomPainter. Если рецепт невалиден — стандартный светлый/тёмный/сепия интерфейс, без блокировки игры. ИИ не исполняется при отображении.

Синхронизация: WorldEvent/SQLite/save — единственный источник игрового состояния; ThemePack содержит только косметические значения. Диалоги показывают подписанные и разрешённые speaker turns; узор/портрет не должен раскрывать скрытый предмет или будущую личность NPC.

## 2.1. Утверждённая технология: общее программное рисование + штатный Flutter UI (без AI-изображений)

**Окончательное решение по вопросу пользователя:** не делать скины в виде сгенерированных нейросетью картинок (PNG, JPG, WebP, spritesheet) и не собирать из заранее нарисованных «скриншотов» окна/кнопки/иконки. Для художественных деталей скина использовать **ту же систему процедурных pixel recipes**, что и для пиксельных сцен. При этом не пытаться пикселями изображать весь интерактивный UI или кириллический текст: Flutter остаётся системой компоновки, ввода и чтения. Это **один гибридный renderer**, не два конкурирующих графических движка.

**Единая программа рисования (Flutter Canvas / CustomPainter, при измеренной необходимости Flame):**
- Общие безопасные опкоды: rect, rounded_rect, pixel_line, polygon, mask, tiled_ornament, 9_slice_procedural_frame, seeded_noise, limited_gradient, palette_remap. Точные названия и типы будут определены отдельной версионированной схемой. Компонент принимает только data-only инструкции с лимитами на количество операций, слоёв, размер фактур и длительность движения.
- **Сцены:** персонажи, здания, природа, предметы, позы, пиксельные жесты. Всё создаётся при отображении из параметров и стабильного seed.
- **Интерфейс:** обрамления окна текста и диалога, углы, орнамент, декоративные тени, предметные слоты, тематические пиктограммы, узоры подложки, элементы HUD. Всё рисует тот же примитивный renderer, но его результат — **декоративный слой под/над нативным Flutter-виджетом**, а не неподвижная картинка вместо кнопки.
- **Не рисовать текст как пиксельное изображение.** Для русских текстов, имён NPC, вариантов выбора, счетчиков и меню использовать Flutter Text/RichText/Selectables и лицензированный кириллический системный шрифт. Поэтому размер шрифта, разметка, выделение текста, доступность/скринридер, фокус клавиатуры и hitbox работают на Android и Windows.
- **Один StyleBible и renderer:** одинаковые палитра, материалы, пиксельная сетка, орнаменты и seeded pattern IDs в сцене, окне текста и инвентаре. На малых экранах декоративная плотность уменьшается, текст/контраст/управление остаются приоритетом.
- **Данные, а не бинарные ассеты:** будущий .bworld хранит только верифицированные JSON recipes в согласованном vNext. Внешний генератор не поставляет обязательных PNG, JPG, JPEG, WebP, SVG, внешних шрифтов, видео, произвольных JS/Dart/шейдеров и ссылок на CDN. Локальные растровые текстуры **могут временно кэшироваться в оперативной памяти** для скорости, но они вычисляются из рецепта и не являются исходными AI-картинками или обязательной частью архива.
- **Не ломать действующий rich-v3:** 4 строго проверенных ZIP-файла остаются неизменны. UI-скин и его pixel opcodes появятся только после writer+importer и native versioned capability; старые игры без скина открываются штатным оформлением.

**Почему это предпочтительнее полностью пиксельного UI:** одно и то же рисование годится для любых жанровых рамок/иконок, но адаптивный текст и доступные нативные кнопки не страдают из-за фиксированной пиксельной сетки. Нельзя заменить основное содержимое диалога картинкой, где пользователь не сможет увеличить текст или выделить слово. И наоборот, только смена ThemeData без программных рамок/орнаментов не даёт уникального книжного оформления. **Выбранное сочетание даёт оба преимущества.**

**Проверка именно этой инварианты:** без исходных растровых файлов и сети скин открывает все UI слоты; изменённый style_seed перестраивает только рисунок; Text/RichText поддерживает кириллицу и scale 100–200%; voice-over/screen reader, focus/keyboard, hitbox, reduce motion, orientation, Windows DPI 150%; никакой decorative overlay не перекрывает текст/кнопки; offline build/reopen даёт один и тот же внешний вид при неизменном seed. Любой неизвестный opcode → безопасный штатный UI.

## 2.2. Шрифты книги — автоматическая типографика, не изображение букв

**Решение:** каждая книга получает собственную типографическую тему из того же StyleBible, что pixel recipes и весь UI. Но основной текст нельзя превращать в пиксельные картинки, самодельный TTF или Canvas-подмену реального Flutter Text: это сломает выбор текста, русскую кириллицу, переносы, масштабирование и доступность. Генератор не генерирует новые font-файлы и не распространяет чужие шрифты с каждой книгой.

**Четыре обязательные роли:**
1. **body / prose:** длинный повествовательный текст; мягкий, проверенный, полноценный кириллический Noto Serif или Noto Sans / одобренный аналог, сохранение настроек читателя. Никогда не использовать декоративный pixel font для целой главы.
2. **dialogue / choices:** реплики, имена говорящих и варианты выбора; обычное читаемое начертание, небольшой стилистический акцент на имени, поддержка кириллицы и длинных фраз.
3. **ui / controls:** все три вкладки, инвентарь, журнал, сохранения, кнопки и подсказки; максимально читабельный Noto Sans / системный fallback, допускается согласованная толщина/spacing.
4. **display / ornament:** заголовок книги, главы, финала, краткие лейблы и буквицы; могут использовать Cormorant Garamond, Russo One или Pixelify Sans с кириллицей. Буквицы и рамочные украшения допустимо рисовать теми же procedural pixel primitives, что сцены, **но не весь текст**.

**Конкретный начальный курируемый набор (проверены GitHub Google Fonts METADATA.pb, licence OFL, subsets cyrillic):** [Noto Serif](https://github.com/google/fonts/blob/main/ofl/notoserif/METADATA.pb), [Noto Sans](https://github.com/google/fonts/blob/main/ofl/notosans/METADATA.pb), [Cormorant Garamond](https://github.com/google/fonts/blob/main/ofl/cormorantgaramond/METADATA.pb), [Russo One](https://github.com/google/fonts/blob/main/ofl/russoone/METADATA.pb), [Pixelify Sans](https://github.com/google/fonts/blob/main/ofl/pixelifysans/METADATA.pb). Лицензия SIL OFL 1.1 в метаданных, но при реализации отдельно фиксировать точную версию семейства, весь текст OFL/NOTICE, font coverage, font-size/license impact. Не копировать/выкладывать файлы шрифтов в эту ветку. Рекомендуется установить ограниченную коллекцию в само Flutter-приложение **один раз** (с лицензиями), а в будущем game.bworld хранить только проверенные family_id/role/weight/spacing. Это сохраняет автономность и не раздувает каждую игру дубликатами TTF.

**Подбор по теме:** сказка — Noto Serif body + Cormorant Garamond display; детектив — Noto Serif или Noto Sans body + контрастный строгий display; научная фантастика — Noto Sans body/ui + Russo One display; ретро-пиксели — Noto Sans body/dialogue + Pixelify Sans только для заголовков/коротких игровых надписей. Достаточно 1–2 семейства на книгу плюс безопасный UI fallback; уникальность возникает из сочетания начертания, размера, межстрочного интервала, буквицы, рамок, цвета и орнамента. Не генерировать совершенно новый алфавит на каждую книгу: стоимость QA несоразмерна пользе.

**Схема (предложение, НЕ поддерживается текущим rich-v3):** typography_roles.body_family_id, dialogue_family_id, ui_family_id, display_family_id, heading_weight, tracking_range, readable_line_height, decorated_initial_style, fallback_family_id; все font IDs — allowlist, никаких внешних URL или произвольных файлов. Токены независимы от GameState/WorldEvents, не влияют на сохранения; одинаковый StyleBible даёт один набор ролей. Пользователь всегда может вернуть обычный шрифт и переопределить размер/интервал; доступный шрифт важнее художественного стиля.

**Обязательная приёмка:** покрытие букв русского языка (включая Ё/ё), кавычек, тире, цифр, редких имен, смешанной латиницы; автоматический glyph-coverage тест с возвратом к Noto/system fallback; 100–200% text scale на Android, Windows DPI 150%, portrait/landscape, 2–3 говорящих, длинное название и очень короткие кнопки; screen-reader/selectable text; отсутствие сети и обновления приложения при открытии конкретной книги. При невозможности использовать выбранный display font интерфейс должен автоматически перейти на доступный семейный fallback, без пропавших символов или квадратиков.

## 3. Все тематические области

| Элемент | Меняется по книге | Никогда не менять через theme |
| --- | --- | --- |
| Окно повествования | фон, фактура, рамка, углы, разделители, цвет акцента | сам текст, скролл, размер hitbox, читабельность |
| Диалоги | рамка, табличка имени, фон портрета, анимация появления | последовательность реплик, speaker ID, knowledge gate, сохранённая позиция |
| Герой | карточки, индикаторы, рамка портрета | реальные характеристики/знания/NPC отношения |
| Предметы | слоты, карточки и графика, тематический контур инвентаря | наличие, фактический NPC владелец, правила передачи |
| Журнал | свиток/досье/хронограф, маркеры событий, линия времени | только committed events, неизменный порядок и последствие |
| Выборы и кнопки | контур, pressed/hover/focus, декор | смысл, доступность, выбор ID, размер касания |
| Меню, сейвы, пауза | фон, орнамент, пиктограммы и заголовок | видимость настроек/выхода/возврата, работоспособность |
| Загрузка и конец | оформленная обложка/финальная панель | достоверность концовки, переходы/состояние |
| Пиксельная сцена | те же краски, материалы, pixel scale и стилистика | факты, персонажи, предметы без источникого подтверждения |

Иконки сохраняют **фиксированный смысл**: hero, inventory, journal, next_dialogue, choice, save, settings, back, close, locked, warning. Тема выбирает только один разрешённый рисунок на semantic icon ID. В случае отсутствия собственного рецепта — штатный Flutter icon. Украшения никогда не становятся интерактивными кнопками сами по себе.

## 4. Автоматический конвейер

После литературной проверки и сборки проверяемого игрового состояния:

A. Проанализировать образы и тон **всей книги**, а не только первой сцены.
B. Создать единый Style Bible и стабильный визуальный seed. Выбрать до 2–4 основных акцентов и заранее обеспечить контрастное «чернило» для длинного текста.
C. Сгенерировать процедурные pixel scene recipes и SkinRecipe из одного Style Bible. Повторяемый узор/рамка/текстуры — ограниченные геометрические примитивы, пиксельные линии, 9-slice frames и заранее разрешённые ornament opcodes.
D. Проверить схемы JSON, все обязательные semantic icons, путь fallback, отсутствие spoiler visuals, допустимые длины/число слоёв, CPU/RAM бюджет.
E. Прогнать визуальные golden/widget проверки для длинного русского текста, 3 собеседников, отсутствующих предметов, 2 устройств и Windows DPI 150%, а также реальный Android/Windows smoke.
F. Только после утверждённой native capability и schema встроить theme в один новый самодостаточный game.bworld вместе с сюжетом. Сама игра без UI-скина обязана оставаться проходимой.

Пользовательские настройки: «Автоматически по книге» (default), «Сдержанный», «Атмосферный», «Пиксельный»; отдельный переключатель «Другой вариант оформления». Режим сцены text/pixels_static/pixels_animated — **независимый** от общего скина. Даже при отключённой графике игровой интерфейс может сохранять лёгкую тематическую рамку.

## 5. Будущий формат и упаковка

Предлагаемая независимая capability — ai_story_ui_theme_recipe_v1. Её структура **только проектная**, не API действующего .bworld v3:

    {
      "format": "ai_story_ui_theme_recipe_v1",
      "source_fingerprint": "<source-sha256>",
      "style_revision": 1,
      "style_seed": "stable-versioned-visual-seed",
      "palette": {
        "surface": "#F2E6CC", "ink": "#282019",
        "accent": "#335746", "focus": "#8B5B16"
      },
      "typography": {
        "body_role": "readable_serif_fallback",
        "title_role": "ornamental_heading"
      },
      "recipes": {
        "story_frame": "illuminated_corners",
        "dialogue_frame": "chapter_card",
        "hero_icon": "crown_outline",
        "inventory_icon": "satchel_outline",
        "journal_icon": "bound_book_outline"
      },
      "accessibility": {
        "reduce_motion_fallback": true,
        "neutral_theme_fallback": true
      }
    }

**Внимание:** пример не является готовой схемой или готовой игровой упаковкой. Отсутствуют утверждённые version, enum и asset sizes. В нынешнем .bworld v3 — **строго четыре ZIP-записи**, добавлять ui/skin.json скрыто НЕЛЬЗЯ. Будущий vNext должен предусмотреть ui/skin.json и visuals/style_bible.json с hashes/sizes, min renderer version, hard resource limits, проверкой Python writer/verifier и Dart importer, обратной совместимостью с v3. Временный private preview sidecar допустим лишь для проверки разработчика, не как конечный обязательный пользовательский файл.

Никаких удалённых URL, HTML, JS, произвольных shaders/opcodes, native binary/script assets, CSS или небезопасных SVG. Разрешён только подписанный список безопасных данных и примитивов. Оформление книги не должно получать доступ к файловой системе или сети и не должно менять действия/состояние игры.

- apps/story_reader/lib/reader_chrome.dart: поведение hide/show и F11/Escape не зависит от скина.
- apps/story_reader/lib/world_library_gateway.dart: события/проекции читаются из движка; skin не изменяет SQLite, item ownership и NPC life.

Native Flutter изменения выполняются в отдельном основном чате после согласования vNext. Внешняя ветка tools/rpg_author готовит только будущие data-only recipes, тесты и нормативный план, не создаёт параллельный UI/runtime.

## 7. Доступность, производительность, безопасность и тесты

- Основной текст: контраст не ниже 4.5:1; крупные пиктограммы/управляющие границы где применимо — не ниже 3:1. Это целевые gate-пороговые значения, которые должны проверяться тестами, а не художественным описанием.
- По умолчанию не встраивать названия в нарисованные текстуры. Русская кириллица, длинные слова, сломанные строки, font scale 100–200%, Windows 150% DPI, Android portrait/landscape — обязательные layout тесты. Шрифты — системные или заранее лицензированные; генератор не создаёт/поставляет сомнительные font files.
- Сохранить светлая/сепия/тёмная/OLED, крупный текст, reduce motion, режим «Обычная тема» и «Отключить оформление книги» в доступных настройках. Декор не закрывает кнопку и не мешает чтению.
- Негативные тесты: неизвестный theme opcode/schema, подмена SHA256 ZIP, повреждённый JSON, огромный ZIP, path traversal, опасные пути/URL, отсутствующая рамка, неверный семантический icon, слишком тёмный текст, раскрытие secret NPC, пиксельная графика выключена, high contrast, resume после закрытия.
- Стабильность: одна книга + один style_seed даёт детерминированные theme recipes. Явная повторная генерация меняет только косметические данные, не game state, источниковые ссылки, персонажей и сейвы.
- Обязательная приёмка: Python generator→archive hash verification→Dart importer→widget golden→SQLite replay→реальный Android+Windows device QA; отсутствие Internet/GLM при чтении не должно менять внешний вид и game rules.

## 8. Приоритеты

**P0:** закончить готовую текстовую RPG по настоящей книге и device E2E. Скин НЕ блокирует это.
**P1-подготовка:** единый Style Bible и ограниченная preview схема отдельно от старого v3, без обещания готового импорта.
**P2 вместе с пиксельными сценами:** полноценный book-specific SkinRenderer, будущий явно версионированный self-contained .bworld и импорт без пересборки программы; общий набор 3 начальных стилей и fallback.
**Позже:** комфортная ручная регенерация/выбор варианта, необязательное редактирование; не отдельный PR на каждую кнопочку.

**Главное UX-правило:** передал книгу — автоматически получил уникальную атмосферную игру. Ни рисование кнопок, ни подбор рамок, ни выгрузка отдельной темы не являются обязательными действиями пользователя.
