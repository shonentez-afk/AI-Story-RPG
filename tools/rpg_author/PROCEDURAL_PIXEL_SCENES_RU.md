# Процедурные пиксельные сцены: архитектурное требование (E6f+)

Дата решения: 2026-11-06. **Статус: согласованное направление, НЕ реализовано.**
Область: внешний автор `tools/rpg_author/` готовит спецификацию; основной Flutter/BookWorld — READ-ONLY до отдельного разрешения. Это не изменение текущего контракта `.bworld v3` и не новый обязательный этап перед завершением E6e.

## Неподменяемое требование пользователя

Генератор должен **самостоятельно создавать пиксельные сцены из кода по содержанию книги**, а не вызывать текст-в-изображение, подставлять готовые фоны/портреты или генерировать PNG-файлы. Художественный результат строится алгоритмами из пикселей, форм, правил композиции, палитр, геометрии и анимаций. Графический буфер/временный in-memory cache при отрисовке допустим: это обычная работа рендерера, не внешний сгенерированный арт-ассет.

- Нельзя делать обязательными заранее нарисованные PNG, SVG, spritesheet, облачную модель рисования или ручную подготовку арт-ресурсов.
- Нельзя исполнять неподтверждённый Python/Dart/JS-код, придуманный моделью, в мобильном приложении. Модель выдаёт только **строго типизированные данные по схеме**; исполняются лишь собственные проверенные алгоритмы визуализации.
- Данные книги не загружать для генерации картинок в сеть; если смысловой анализ книги использует облачный ИИ, он допускается только по уже установленному явному согласию и правилам приватности.
- Отсутствие визуальной постановки НЕ блокирует чтение, диалог или игру; fallback — текущий текстовый интерфейс.

## Три независимых слоя

1. **Каталог книги**: постоянные `character_id`, `location_id`, `source_event_id`, `item_id`, проверяемые цитаты, мотивы/знания/временные пометки с неопределённостями. Не путать повествовательный порядок с мировым временем.
2. **Игровой сценарий**: `scene_id`, `choice_id`, флаги, предметы, знания, журнал, последовательность сцен. Единственный источник истины — действующий `story_core`/SQLite/BookWorld.
3. **Процедурная постановка**: `scene_visual_recipe` + `actor_visual_recipe` + `visual_cues`; детерминированный рендерер строит изображение прямо в Flutter/Flame Canvas. Визуальная постановка не может менять игровой мир.

Изменение расположения блоков в визуальном редакторе не меняет сценарий; редактирование `choice_id`/условия/эффекта создаёт новую ревизию и инвалидирует старые проверки.

## Грамматика генератора и renderer

**Сцены:** локация/эпоха/время суток/погода/настроение, планы дальний-средний-передний, декорации, позы, действия и источники. Не ограничиваться сказочными лесом/замком: предусмотреть расширяемые архетипы города, деревни, дома, улицы, производства, дороги, природы, корабля и нейтральной неизвестной локации.

**Рисование:** логическая сетка порядка 320×180 или меньше, строго целочисленные координаты и размеры. Пиксельные прямоугольники, шаблоны масок, контуры, палитры, повторяемые формы, шум с фиксированным seed, процедурная геометрия построек/деревьев/воды/одежды/лиц; без сглаживания и без импорта заранее нарисованных спрайтов.

**Персонажи:** постоянный `character_id`, детерминированный `appearance_seed` + явно допустимые свойства из проверенного каталога. Лицо, фигура, цвет, одежда, выражения, положение тела и походка рисуются кодом (маски пикселей и геометрические примитивы). При отсутствии оснований не придумывать достоверную внешность, использовать нейтральную/редактируемую стилизацию. Один герой должен оставаться узнаваемым между сценами и перезапусками.

**Анимация:** кодовые состояния `idle`, `talk`, `walk`, `turn`, `give`, `take`, `appear`, `disappear`, `react`; таймлайн из ограниченного каталога команд. Лягушонок всплывает, протягивает мяч, меняет позу; игровое получение предмета происходит ТОЛЬКО после разрешённого выбора story_core, не от завершения анимации.

**Детерминизм:** `scene_visual_id`, `renderer_version`, `source_fingerprint`, `story_sha256`, seed и параметры. Одна ревизия + один игровой state -> тот же состав декораций/персонажей и базовый кадр. Временные колебания анимации не меняют игровые факты; после загрузки восстановить визуальные состояния по достоверному snapshot игры.

**Производительность:** группировать смежные пиксели одного цвета и статические слои, не вызывать десятки тысяч `drawRect` каждый кадр; ограничивать число объектов/переходов и бюджеты памяти. В первом прототипе достаточно `CustomPainter`/Flutter Canvas; для полноценной анимации использовать Flame `GameWidget`, `ShapeComponent` и `CameraComponent.withFixedResolution`. UI диалогов/героя/предметов/журнала остаётся Flutter поверх сцены.

## Пример БУДУЩЕЙ схемы (не поддерживается нынешним компилятором!)

```json
{
  "format": "ai_story_procedural_visuals_v1",
  "source_fingerprint": "<sha256 исходной книги>",
  "story_sha256": "<sha256 проверенного сценария>",
  "renderer_version": "1",
  "scene_id": "pond_meeting",
  "appearance_seed": 42,
  "stage": {
    "location_id": "forest_pond",
    "layout": "side_view",
    "time": "day",
    "weather": "clear",
    "palette": "storybook_16",
    "layers": ["sky", "trees", "water", "shore", "actors", "foreground"]
  },
  "actors": [
    {"character_id": "princess", "archetype": "humanoid", "at": [80, 140], "pose": "idle"},
    {"character_id": "frog", "archetype": "frog", "at": [220, 154], "pose": "idle"}
  ],
  "props": [
    {"item_id": "golden_ball", "shape": "orb", "owner": "player", "visible_when": {"has_item": "golden_ball"}}
  ],
  "cues": [
    {"on": "scene_enter", "actor_id": "frog", "animation": "appear"},
    {"on": "dialogue_turn", "turn_id": "frog_greeting", "actor_id": "frog", "animation": "talk"},
    {"on": "choice_committed", "choice_id": "accept_promise", "actor_id": "frog", "animation": "give"}
  ]
}
```

Пример показывает структуру, а НЕ готовый API. Поля проверять по строгому allowlist и точным ID текущего сюжета, не исполнять строки как код. Условие `visible_when` должно ссылаться на реальные разрешённые игровые факты: игровое состояние, а не визуальный скрипт, решает принадлежность предмета. В реальном примере появления мяча не допускать спойлера/ложного владельца. При спорной цитате сцена должна маркироваться как недоказанная или как `EXPLICIT_ADAPTATION`.

## Граница совместимости

- Действующий `.bworld v3` — строго четыре записи ZIP; нельзя тихо добавлять `visuals.json` или менять поле `scenario/blueprint.json`. Для первого прототипа хранить отдельный приватный `procedural_visuals.json`, привязанный к SHA текущего игрового мира и исходнику. Экспорт/импорт такого sidecar не считается работающим до реализации его проверок в приложении.
- Переносимая встроенная процедурная постановка потребует отдельного версионированного контракта и независимых Python/Dart проверок; не ломать нынешний v3.
- Внешний генератор создаёт и валидирует recipe/таймлайн; Flutter-клиент исполняет проверенный рендерер. Внешний генератор НЕ должен генерировать APK/исполняемые Dart-файлы отдельно для каждой книги.

## Реализация по этапам (НЕ растягивать текущую генерацию книги)

1. После E6e/E6f и каталога книги — `visual-plan` для одной выбранной сцены, строгое JSON-schema и проверки связей со сценами, событиями, персонажами, знаниями и выборами. Без изменения `.bworld`.
2. В отдельной тестовой среде — Dart-процедурный рендерер на Canvas: кодовая сцена у пруда, два генерируемых персонажа, один предмет, смена `talk/give/idle`; никакого PNG/GIF/LLM image input.
3. Запуск Windows/Android: одинаковая идентичность персонажа, правильная смена визуальных состояний после *подтверждённого* игрового выбора, возобновление, офлайн, сохранение доступности вкладок и диалогов, ограничение ресурсов и fallback.
4. Лишь после согласования импорта: карты нескольких локаций, расширяемый каталог генераторов, пользовательский визуальный редактор, необязательное пакетирование проверенного visual recipe.

Приёмка: никакой обязательной графики-файла, отсутствие сетевых запросов для рисования, стабильный seed, согласованный source/story/world hash, отсутствие вымышленных предметов/знаний/спойлеров, проверка того, что визуальные события **никогда** не вызывают коммит story_core сами.

## Изученные ориентиры (переиспользовать идеи, не делать JS runtime зависимостью)

- Flame Shapes: https://docs.flame-engine.org/latest/flame/components/shape_components.html — геометрические примитивы.
- Flame GameWidget: https://docs.flame-engine.org/latest/flame/game_widget.html — встраиваемая игровая сцена в Flutter.
- Flame Camera: https://docs.flame-engine.org/latest/flame/camera.html — фиксированная логическая область.
- PixelForge: https://github.com/KodoRe/pixel-forge — JSON/seed/palette/procedural humanoid/animal/tile; **JS-пример концепции**, не подключать его в Android/Windows Flutter непосредственно.
- sprite-forge: https://github.com/paperhurts/sprite-forge — детерминированные кодовые слои внешности (одежда/волосы/эмоции).
- pixel-sprite-generator: https://github.com/zfedoran/pixel-sprite-generator — маски/симметрия/рандомизация; не считать алгоритм распознавания книжных персонажей.
- Не использовать нейросетевые проекты text-to-image как реализацию этого требования.

**Ограничение качества:** для незнакомых объектов/эпох уникальные процедурные формы и узнаваемая мимика могут потребовать новых правил и ручной правки. Грамматический рендерер не гарантирует точное визуальное понимание любой книги. Программа должна открыто показывать неопределённости и не создавать ложные канонические детали.
